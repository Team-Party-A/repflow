# 需求规格说明书：watchOS App

版本：v1 章节评审稿；日期：2026-10-20；章节作者：Iridescent（whj，@whj-thu）。关联子任务：[#19](https://github.com/Team-Party-A/repflow/issues/19)；父任务：[#7](https://github.com/Team-Party-A/repflow/issues/7)。

本章按[统一需求骨架](需求规格说明书.md)编排，沿用已合入的[术语表](../design/术语表.md)与 [UI 规范](../design/UI规范.md)。本次交付是需求与验收方案；下列用例尚未执行，不表示已完成 App、真机测试或全组评审。已有决策之外的行为细化是评审提案，待决项见第 8 节。

## 1. 范围与跨端边界

依据[第 1 次例会纪要](https://github.com/Team-Party-A/repflow/wiki/第-1-次例会纪要) D-02、D-03、D-16：

- Must 主流程：开组前手动选择动作 → 开始本组 → 自动计次 → 结束本组 → 核对／修正 → 确认并保存到手表 → 传到手机。组间休息自动识别为 Should，不阻塞主流程。
- 手表负责训练现场的选动作、组边界、计次展示、本地保存与记录交接；手机负责账号、历史、记录增删改查和上传后端。自动计次后修正仍属于「自动计次」来源，不改成「手动」。
- 训练模板沿用 REQ-IOS-012 的 Should；是否传到手表待评审。自动识别动作是 Could；本章不加入心率、热量、恢复评分或云端在线计次。
- 在线计次沿用 Swift；算法评估与误差门槛引用 [04 章节](04-alg-web.md)。手表到手机沿用[可行性分析](可行性分析.md)的 WatchConnectivity 方向，不引入第二套传输渠道；消息、确认协议及存储结构留待契约评审。
- 全局最低系统、离线与同步时延分别引用 REQ-NFR-001、REQ-NFR-002、REQ-NFR-003；本章不另设未经评审的秒数或容量门槛。

| 现有跨端需求 | 本章补充的手表侧行为 |
| --- | --- |
| REQ-ALG-001、REQ-ALG-002 | 明确选动作、开组与结束入口、核对操作及保存反馈；不重复定义计次算法及误差指标。 |
| REQ-ALG-003、REQ-NFR-405 | 呈现权限／采样异常；落腕持续采样沿用已有真机用例。 |
| REQ-IOS-003、REQ-NFR-002 | 补齐手表断连暂存、补发、手机持久化接收确认；手机负责接收去重。 |
| REQ-IOS-011、REQ-BE-004、REQ-BE-007 | 手表交接不等于后端同步；上传由手机继续完成。 |
| REQ-ALG-004 | 补充休息状态的手表操作与人工纠正，不新增一套识别算法需求。 |

## 2. 选择动作与组内计次

### REQ-WATCH-001：开组前手动选择动作

- **用户故事**：作为训练者，我希望在手表上先选择要练的动作，以便算法按该动作计次，记录中也能看出练了什么。
- **MoSCoW**：Must。覆盖 D-02「开组前手动选动作」。
- **验收标准**：
  1. 给定已准备好的动作列表，当打开选动作页并选择一项，那么显示选中状态和动作名称；未选动作时不能启动自动计次。
  2. 给定选择了受支持动作，当点「开始本组」，那么计次页显示同一动作；开组前改选动作后，以最后选定项为准。
  3. 给定动作不支持自动计次，那么标明「仅手动」并说明可在手机手动记录，不提供可启动自动计次的入口；不会伪装成已识别或已支持。
  4. 给定手表与手机断连、动作列表已在手表可用，那么仍能选受支持动作并进入本地训练流程。
- **负责模块**：watchOS（@whj-thu，主要实现方）、算法（@shooterli，支持动作范围）。
- **来源**：D-02；REQ-ALG-001；UI 规范第 4、6 节。
- **待决问题**：首批支持动作、完整周期、佩戴侧与单侧／双侧口径见 Q1；UI 中的示例动作不代表支持名单已经冻结。

### REQ-WATCH-002：开始本组并展示自动计次

- **用户故事**：作为训练者，我希望明确开始一组并在手表上看到估计次数，以便训练中无需逐次操作。
- **MoSCoW**：Must。覆盖 D-02「组内自动计次」的手表入口与展示。
- **验收标准**：
  1. 给定已选受支持动作且所需权限、采样条件满足，当点「开始本组」，那么新组从 0 次开始，显示动作、当前组序号、「估计次数」及「结束本组」入口；重复点击不会开启并行的第二组。
  2. 给定算法为当前组输出计次结果，当结果更新，那么显示该组估计次数；真实动作准确性按 REQ-ALG-001、REQ-NFR-403、REQ-NFR-404 验收，不以手工点按模拟作为通过证据。
  3. 给定尚未开组或已经结束本组，当拿放器械或继续活动，那么不增加该组次数；下一组从 0 开始，不带入上一组缓存。
  4. 给定组内短暂停顿后继续动作，那么仍是同一组，不因静止自动保存或开新组；组内不能直接改换动作而继续累加。
  5. 给定所需权限被拒绝或传感器不可用，那么说明原因和恢复操作，不显示正常「自动计次中」。计次中发生采样异常时，按 REQ-ALG-003 显示「计次可能不准」及核对／结束入口，保留已有确认记录，不凭空补次数。
- **负责模块**：watchOS（@whj-thu，主要实现方）、算法（@shooterli）。
- **来源**：D-02、D-03；REQ-ALG-001、REQ-ALG-003；术语表「组内停顿」。
- **待决问题**：权限与后台运行方案、异常阈值及恢复策略见 Q5；首批设备验证不得用仅前台运行结果替代落腕场景。

## 3. 结束、核对与保存

### REQ-WATCH-003：结束本组并核对候选次数

- **用户故事**：作为训练者，我希望结束当前组后核对或修正次数，以便保存的是我确认过的结果。
- **MoSCoW**：Must。承接 REQ-ALG-002 的核对与修正交互。
- **验收标准**：
  1. 给定本组正在计次，当点「结束本组」，那么停止接受该组新增计次并进入「待核对」；显示候选次数和「确认并保存」，此时不显示「已保存」。
  2. 给定估计次数为 9，当通过次数修正控件改为 10，那么候选最终次数为 10，原估计仍可区分；再拿放器械或重复进入核对页不继续计次，也不生成另一组。
  3. 给定输入负数或非整数，那么不能作为最终次数保存，并给出明确提示；1 次、2 次短组可核对保存，不设「至少 3 次」的隐含门槛。0 次组按 Q2 评审，未定前不得静默进入有效训练记录。
  4. 给定本组尚未保存，当点「放弃本组」，那么先确认将丢弃当前候选结果；取消则保留候选，确认则只丢弃本组，其他已确认组不变。
- **负责模块**：watchOS（@whj-thu，主要实现方）、算法（@shooterli，估计结果与修正语义）。
- **来源**：REQ-ALG-001.5、REQ-ALG-002；术语表「结束组」「待核对」「放弃本组」。
- **待决问题**：次数上限、0 次与空训练规则见 Q2；保存估计值及修正标记的具体字段随契约确认。

### REQ-WATCH-004：确认后保存到手表

- **用户故事**：作为训练者，我希望确认一组后即使手机不在身边也能保存，以便继续下一组而不丢记录。
- **MoSCoW**：Must。支撑自动计次闭环与 REQ-NFR-002 的本地保存。
- **验收标准**：
  1. 给定合法候选结果，当点「确认并保存」且持久化成功，那么保存本组所属训练、动作、最终次数与自动计次来源，显示「已保存到手表」及相应传输状态；未修正时最终次数等于估计次数。
  2. 给定第一组已保存 8 次、第二组由 9 改为 10，当保存第二组并重复点击确认，那么仍只有两组，分别为 8 和 10；本次训练已确认组数为 2、动作总次数为 18。
  3. 给定手表无法联系手机或手机无法访问后端，当确认本组，那么仍可本地保存并开始下一组，显示「待传到手机」，不会显示后端「已同步」。
  4. 给定本地写入失败，那么显示「保存失败」及重试入口，在当前界面保留候选结果，不显示「已保存」或清空候选；解除故障重试成功后只保存一份。
- **负责模块**：watchOS（@whj-thu）。
- **来源**：REQ-NFR-002；REQ-ALG-002.5、REQ-ALG-002.6；UI 规范第 6.1 节。
- **待决问题**：本地容量与保留期见 Q4；未保存候选在进程异常退出后的恢复保证见 Q5，不与已保存记录的持久化保证混淆。

### REQ-WATCH-005：继续下一组与结束整次训练

- **用户故事**：作为训练者，我希望在同次训练中继续练习，也能明确结束整次训练，以便手机上的训练归组正确。
- **MoSCoW**：Must。区分「结束本组」与「结束训练」，支撑训练记录归属。
- **验收标准**：
  1. 给定本组已确认保存，当开始下一组，那么新组仍属于当前训练、估计次数从 0 开始，先前已确认组不变；开始前可重新选择动作。
  2. 给定有已确认组且无计次中／待核对组，当点「结束训练」，那么结束当前训练活动并保留全部已确认组；下一次训练与本次分开，不能把新组追加到旧训练。
  3. 给定仍在计次中，当尝试结束训练，那么先提示结束本组并核对；给定已有待核对组，那么提示选择「返回核对」或经确认「放弃本组并结束训练」，不能自动保存候选或无提示丢弃。
  4. 给定选择返回核对，那么保持当前候选与已确认组；选择放弃并结束时只丢弃当前未保存组。存在待传到手机的已确认组时，结束训练不清除它们，仍可后续补发。
- **负责模块**：watchOS（@whj-thu，主要实现方）、iOS（@wenshare71，训练归组接收）。
- **来源**：术语表「训练」「结束训练」；REQ-IOS-003、REQ-IOS-005。
- **待决问题**：训练开始入口、训练身份及结束信息如何交接见 Q3；未确认组处理为本章评审提案。没有任何已确认组时按 Q2 处理，不静默生成有效空训练。

## 4. 手表到手机交接

### REQ-WATCH-006：断连暂存、恢复补发与接收确认

- **用户故事**：作为训练者，我希望手表记录在手机重新可用后自动送达，并知道手机是否已保存，以便不必重复录入。
- **MoSCoW**：Must。支撑 REQ-IOS-003 与 REQ-NFR-002，不替代手机到后端同步。
- **验收标准**：
  1. 给定已在手表保存一组且未获手机保存确认，那么保留该组与待传输状态；即使发送调用返回成功，也不把它当作手机已持久化。
  2. 给定两端断连时手表确认了两组 8 次、10 次，当同一账号归属下两端恢复可传输条件，那么自动补发，两组在手机同一次训练下各出现一次，最终次数分别为 8 和 10，来源为「自动计次」。
  3. 给定同一组重复送达，或手机已保存但接收确认丢失后重发，那么仍指向同一训练和组，手机只保留一份；手表得到对应组的持久化确认后才显示「已传到手机」。
  4. 给定手机收到记录但尚未本地保存成功，那么不能发出保存成功确认；手表仍保留待传记录。明确传输失败时显示「传到手机失败」与重试入口，重试不清除数据或创建新组身份。
  5. 给定手机已保存、但手机断开外网，那么手表可显示「已传到手机」，手机显示「待同步」；只有后端按 REQ-IOS-011、REQ-BE-007 确认当前修改，手机才显示「已同步」。
  6. 给定待传记录属于账号 A、手机切换到账号 B，那么不得直接以 B 的身份接收并上传 A 的记录；归属无法确认时保留待传内容并提示在手机处理账号状态，恢复路径按 Q3 对齐。
- **负责模块**：watchOS（@whj-thu，主要实现方：暂存、补发与状态）、iOS（@wenshare71：持久化、去重与接收确认）；后端（@hulaoyagg，参与账号归属约定）。
- **来源**：D-03；REQ-IOS-003、REQ-BE-003；REQ-NFR-002；术语表「手表到手机传输」「去重」。
- **待决问题**：训练／组身份、接收确认协议、乱序与旧记录处理、账号交接见 Q3；补发节奏与缓存清理见 Q4。本条约定用户可观察的交接结果，不冻结字段、API 或具体 WatchConnectivity 方法。

## 5. 组间休息（Should）

### REQ-WATCH-007：展示休息状态并保留人工控制

- **用户故事**：作为训练者，我希望组间能查看休息状态和时长，并能自己开始下一组，以便按实际训练节奏继续。
- **MoSCoW**：Should。对应 D-02「组间休息自动识别」，Must 流程稳定后实现。
- **验收标准**：
  1. 给定算法按 REQ-ALG-004 判定进入组间休息，那么手表显示休息状态；自动判定不直接确认保存候选组，也不把组内短暂停顿当成新组。
  2. 给定休息计时已开始，当用户核对并修正上一组次数，那么计时不重置；显示「已休息」或「剩余休息」以对应评审后的正计时／倒计时规则。
  3. 给定休息误判，用户可纠正状态；给定上一组已确认或已明确放弃，用户可人工开始下一组，无须等待休息自动结束。休息状态本身不累计动作次数。
  4. 给定休息识别未启用或不可用，那么仍可人工结束本组、核对、保存并开始下一组；不得将休息识别作为 Must 流程的前置条件。
- **负责模块**：watchOS（@whj-thu，主要实现方：展示与操作）、算法（@shooterli，休息识别）。
- **来源**：D-02；REQ-ALG-004；UI 规范「休息计时」。
- **待决问题**：休息起点、计时方向、默认时长、短暂停顿阈值与误判纠正入口见 Q6；本章不默认增加休息提醒或自动开组。

## 6. 非功能需求

### REQ-NFR-201：已保存组及待传状态持久化

- **用户故事**：作为训练者，我希望手表 App 退出或设备重启后，已经确认保存的组仍能找回并传到手机。
- **MoSCoW**：Must。细化 REQ-NFR-002 的手表断连暂存。
- **验收标准**：
  1. 给定两端断连时已在手表保存两组 8 次、10 次，当退出 App 并重启手表，那么两组的训练归属、动作、最终次数及待传状态仍在；连接恢复后按 REQ-WATCH-006 送达且不重复。
  2. 给定写入失败或存储空间不足，那么不报告保存成功、不静默淘汰尚未获手机保存确认的组，按 REQ-WATCH-004.4 提示处理。
  3. 给定已有确认组，当另一个组计次异常、被放弃或训练结束，那么此前保存结果及待传任务不被清空。
- **负责模块**：watchOS（@whj-thu，主要实现方）、iOS（@wenshare71，恢复交接验证）。
- **来源**：REQ-NFR-002；REQ-IOS-003；术语表「本地保存」。
- **待决问题**：保留期、积压上限与已接收数据的清理策略见 Q4；卸载 App、解除配对、换机后的恢复不在本条已保存保证内，需另行评审。

### REQ-NFR-202：关键操作可读、可触达且状态可区分

- **用户故事**：作为训练者，我希望在小屏和放大文字时仍能看懂次数与状态，并完成开组、核对和保存。
- **MoSCoW**：Must。保障核心操作可用；具体视觉取值沿用 UI 规范的评审约定。
- **验收标准**：
  1. 在团队使用的 41 mm、45 mm 布局及默认／放大文字设置下，走通选动作、开组、结束、核对、保存，动作名称、次数、错误提示与操作文字不因截断而无法理解，必要时可滚动触达。
  2. 开启 VoiceOver 后，动作、估计次数、增减次数及保存入口有明确标签，计次更新不会逐次打断正在进行的朗读；主要操作触控范围按 UI 规范检查。
  3. 分别展示计次中、待核对、保存失败、已保存到手表、待传到手机与传输失败；仅凭文字和图标也能区分，不仅依赖颜色。
- **负责模块**：watchOS（@whj-thu）。
- **来源**：UI 规范第 3–6 节；术语表「容易混淆的表达」。
- **待决问题**：实际测试机型与可用的大字号档位在原型评审记录；布局预览不替代最低版本真机验证。

最低系统与落腕持续采样直接沿用 REQ-NFR-001、REQ-NFR-401、REQ-NFR-405，不新增重复编号。需在 watchOS 9.6.3 最低版本真机执行核心流程及落腕场景，记录设备、系统、时长、采样中断和实际结果；未通过不能宣称兼容。算法回放按 REQ-NFR-406 与真实训练隔离，不进入历史、统计或正常上传。

## 7. 覆盖与验收走查

D-02 的手表 Must「开组前手动选动作，组内自动计次」由 REQ-WATCH-001、REQ-WATCH-002 与 REQ-ALG-001 联合覆盖；核对、保存及交接由 REQ-WATCH-003–006 衔接。账号、完整记录增删改查、历史统计、后端上传仍由 iOS／后端章节负责；自动休息只对应 REQ-WATCH-007（Should）。
