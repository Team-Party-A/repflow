# RepFlow 可行性分析

版本：v1 评审稿（2026-10-18）。作者：@wenshare71。关联任务：[#8](https://github.com/Team-Party-A/repflow/issues/8)。

## 结论

| 维度 | 结论 | 主要前提 |
| --- | --- | --- |
| 技术 | 可行，计次准确率尚无实测 | 第 8 周用真机验证免费 Apple ID 下的 workout session 与 WatchConnectivity |
| 时间 | Must 能在迭代 2 检查（第 12 周，12-03）前完成，余量约 0.5 个迭代 | 「历史与统计」按最小版本提前到迭代 1–2；计次按 #12 的降级方案兜底 |
| 人力 | 可行，四个模块各有一名负责人，三台手表够采集和联调 | 每人每周约 8 小时；组长无手表，靠模拟器与回放开发，真机联调放在每周集中开发 |

范围以 D-02（MoSCoW）、D-03（三条接口取最简方案）、D-07（免费 Apple ID）、D-08（分工）、D-16（最低系统版本）为准，见 [第 1 次例会纪要](https://github.com/Team-Party-A/repflow/wiki/第-1-次例会纪要)。

## 1. 技术可行性

### 1.1 Watch 传感器计次

结论：**可行，但只对腕部运动明显的动作有把握**。详见 [计次可行性调研](../algorithm/计次可行性调研.md)（#12）。

| 问题 | 判断 | 依据 |
| --- | --- | --- |
| 能否拿到信号 | 能 | Core Motion 的 `CMDeviceMotion` 提供去重力加速度、角速度、重力和姿态 |
| 算法复杂度 | 低到中 | 首选「平滑 + 峰值候选 + 完整周期校验」，Swift 数组加少量状态即可，不需要新框架 |
| 落腕后能否持续采样 | 需验证 | 依赖 watchOS 训练会话（`HKWorkoutSession`）和后台模式，需 HealthKit 权限 |
| 准确率 | 未知 | 尚无本组录制数据；评审目标为每组误差 MAE ≤ 1 次（待评审） |

### 1.2 手表 ↔ 手机传输

结论：**可行**。按 D-03 只用 WatchConnectivity 一种方式。

| 场景 | 方式 | 说明 |
| --- | --- | --- |
| 一组结束后发送记录 | `transferUserInfo` | 系统排队、手机不在线时稍后送达，适合「不能丢」的数据 |
| 训练中实时显示（可选） | `sendMessage` | 需要两端都在前台且可达，不可达时不发，不作为唯一通道 |
| 去重 | 每组带唯一 ID | 重复送达时手机端按 ID 去重，与 REQ-NFR-002 的「只出现一次」一致 |

消息格式写进第 8 周冻结的接口契约，本文不定义。

### 1.3 免费 Apple ID 的限制（D-07）

结论：**开发和演示够用，需要按下表规避**。下列限制来自 Apple 文档和社区经验，第 8 周搭工程时在真机上逐条核实。

| 限制 | 影响 | 应对 |
| --- | --- | --- |
| 描述文件 7 天过期，过期后 App 打不开 | 演示当天可能打不开 | 每次检查前 2 天在演示设备上重新安装（已写入长期规划的「检查前 2 天」） |
| 每台设备同时最多装 3 个免费签名的 App | iOS App 与 watchOS App 共占 2 个 | 组员真机上不再装其他自签 App |
| 每个账号每 7 天最多注册 10 个 App ID | 频繁改 Bundle ID 会被锁 | Bundle ID 一次定好，不随分支变 |
| Bundle ID 只能被一个账号注册 | 四人用各自的 Apple ID 签名会冲突 | Bundle ID 加个人后缀，用不入库的 `.xcconfig` 注入 |
| 不支持推送通知、Sign in with Apple、iCloud 等能力 | — | 需求已避开（账号只用用户名 + 密码 + token，D-03） |
| 真机需开启开发者模式 | 首次安装多一步 | 写进 iOS/watchOS 工程的 README |

HealthKit 和后台模式在免费账号下可用（D-07 的前提），但 `HKWorkoutSession` 在 watchOS 9.6.3 真机上能否落腕持续运行，是第 8 周第一项要验证的事。

## 2. 时间可行性

结论：**按现有阶段划分，Must 能在迭代 2 检查前完成，但「历史与统计」原排在迭代 3，需要前移**。

### 2.1 Must 与阶段检查对照

| 周 | 检查 | 本阶段完成的 Must | 退出条件 |
| --- | --- | --- | --- |
| 8（11-05） | 检查 1：中期汇报 | — （契约冻结、骨架上线、CI 跑通） | 契约冻结；健康检查接口可访问 |
| 10（11-19） | 检查 2：迭代 1，v0.1 | 账号；训练记录增删改查（手机手动录入）；同步到后端；历史列表 | 手机记一次训练，后端能查到 |
| 12（12-03） | 检查 3：迭代 2，v0.2 | 开组前选动作 + 组内自动计次；手表 → 手机同步；基础统计 | 戴手表做一组，自动计次并同步到后端 |
| 14（12-17） | 检查 4：迭代 3，v0.3 | — （Should：Web 看板、训练模板等；统计可视化完善；内测） | 内测反馈转成 Issue |
| 15（12-24） | 检查 5：展示汇报，v1.0 | — （只修不加） | 答辩完成 |

所以 Must 全部落在第 8–12 周，共 5 周；迭代 3、4 留给 Should、内测和文档。

### 2.2 判断依据

| 依据 | 说明 |
| --- | --- |
| 迭代 1 不依赖手表 | 账号、增删改查、上传都只涉及手机和后端，手表与算法风险不会拖住 v0.1 |
| 算法与迭代 1 并行 | 第 8 周录制工具就绪后，迭代 1 期间完成采集、标注和离线评估（#12 第 5 节），迭代 2 只做 Swift 落地和联调 |
| 「历史与统计」最小化 | 迭代 1 做历史列表，迭代 2 做基础统计（如按动作的总组数、总次数），可视化完善留到迭代 3 |
| 余量 | 迭代 2 的两周里，计次落地和三端联调最紧；若第 12 周计次未达门槛，按 #12 降级方案保留手动修正，Must 链路不断 |

### 2.3 时间风险点

- 第 8 周同时有中期汇报、契约冻结和开始写代码，是全程最挤的一周。
- 计次准确率要等录制数据出来才知道，最早在第 10 周前后。
- 第 15 周展示后第 16 周（12-31）还有成果交付，文档不能拖到最后一周。

## 3. 人力可行性

结论：**可行**。分工按 D-08，四个模块各有一名负责人，不存在一人兼两个代码模块的情况。

### 3.1 分工与设备

| 成员 | 主责 | 横向职责 | Apple Watch | Mac |
| --- | --- | --- | --- | --- |
| Wensharre | iOS App | 组长：接口契约、集成 | 无 | 有 |
| Iridescent | watchOS App | 文档负责人 | 有 | 有 |
| hulaoya | 后端、部署、CI/CD | API 文档、部署文档 | 有 | 有 |
| Nessa | 数据与算法；迭代 3 做 Web 看板 | 测试负责人 | 有 | 有 |

### 3.2 投入估算

按每人每周约 8 小时（含每周一次 2–3 小时的线下集中开发，D-17）。Must 阶段（第 8–12 周）约 4 人 × 8 小时 × 5 周 = 160 人时。

| 模块 | 第 8–12 周的主要工作 | 负责人 |
| --- | --- | --- |
| iOS | 工程骨架、账号、增删改查、上传、历史与基础统计、接收手表数据 | Wensharre |
| watchOS | 工程骨架、录制模式、选动作与开组、计次落地、发送到手机 | Iridescent |
| 后端 | openapi.yaml、数据库、账号与记录 API、docker compose、CI、部署文档 | hulaoya |
| 算法 | 录制格式、录制与标注、离线评估、与 watchOS 一起落地 Swift、测试计划 | Nessa |

iOS 的工作项最多，又兼组长事务，是人力上最紧的一处。按 D-08 预案，进度落后时统计可视化移交 Iridescent。

### 3.3 设备约束

| 约束 | 影响 | 应对 |
| --- | --- | --- |
| 组长没有手表 | iOS 端接收手表数据无法独立真机测试 | 先用配对的 iPhone + Watch 模拟器测 WatchConnectivity，再用回放数据模拟传感器；真机联调放在每周集中开发，借组员的手表 |
| 三台手表系统版本不同 | 最低版本兼容性需单独验证 | 按 D-16 部署目标定为 watchOS 9.6.3，在最低版本那台真机上验收 |
| 三名佩戴者 | 正好够 #12 的按人留一评估 | 采集按 #12 第 5 节执行 |

## 4. 主要风险及应对

按「影响 × 可能性」排序。计次相关风险的结论引自 [计次可行性调研](../algorithm/计次可行性调研.md) 第 1、7 节。

| 风险 | 可能性 | 影响 | 应对 | 负责人 |
| --- | --- | --- | --- | --- |
| 计次准确率达不到门槛 | 中 | 高 | 首批只验证腕部运动明显的动作（弯举、肩推）；腕部静止或交替单侧动作不承诺；未达标的动作标为「暂不支持自动计次」，保留手动修正；不把纯手动计数说成完成自动计次 | Nessa、Iridescent |
| 落腕后采样中断 | 中 | 高 | 第 8 周先验证 workout session；采样中断时停止自动累加，提示用户核对 | Iridescent |
| 免费描述文件在演示前过期 | 高 | 中 | 检查前 2 天重装演示设备，并录制备用演示视频 | Iridescent（演示准备） |
| 组长无手表，手表 ↔ 手机联调滞后 | 中 | 中 | 模拟器 + 回放先行；契约第 8 周冻结；每周集中开发做真机联调 | Wensharre |
| 第 8 周任务过于集中 | 高 | 中 | 中期汇报材料在第 7 周完成；契约评审提前到第 7 周例会 | Wensharre |
| 迭代 2 计次与联调挤在两周 | 中 | 中 | 采集和离线评估在迭代 1 并行完成；迭代过半 Must 完成不到一半时，例会第一项讨论砍什么 | 全员 |
| iOS 负责人兼组长，工作量过大 | 中 | 中 | 统计可视化按 D-08 移交 Iridescent | Wensharre |

进度落后时，按 [长期规划](https://github.com/Team-Party-A/repflow/wiki/长期规划) 第四节的降级阶梯先砍 Should 和 Could，Must 链路、单元测试与 CI、部署合规不砍。
