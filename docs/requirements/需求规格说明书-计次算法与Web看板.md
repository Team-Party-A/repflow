# 需求规格说明书：计次算法与 Web 看板

版本：v2 章节评审稿；日期：2026-10-15；章节作者：Nessa（@shooterli）。关联任务：[#7](https://github.com/Team-Party-A/repflow/issues/7)。

## 1. 汇总约定

本文提供 #7 中由 Nessa 负责的“计次算法与 Web 看板”章节。统一规格说明书骨架及 REQ 编号规则尚未合入，因此先使用 `REQ-ALG-xx`、`REQ-WEB-xx`、`REQ-NFR-ML-xx` 作为临时且互不重复的章节编号；组长汇总时转换为统一编号，保留对应关系。本文不替代账号、训练记录 CRUD、watchOS 交互和后端同步负责人应写的章节，也不表示 #7 整体已完成。

范围以 [第 1 次例会纪要](https://github.com/Team-Party-A/repflow/wiki/第-1-次例会纪要) D-02/D-03/D-08/D-16 为依据：

- Must：开组前手动选动作、组内自动计次，以及记录/历史/统计/后端同步的核心链路。
- Should：组间休息自动识别、训练模板、迭代 3 的 Web 数据看板。
- Could：自动识别动作、按恢复情况生成训练计划。
- Won't：社交、Android/Wear OS、上架 App Store。
- Swift 执行在线计次；Python 仅用于离线评估；账号及手机到后端同步遵循团队已通过的简化原则。

长期规划页曾将 Web 看板列为 Could，与 D-02 及 #7 的当前任务范围不一致；本文按已表决纪要采用 Should，若范围调整需在需求评审确认。以下新增的具体行为及量化门槛均为评审提案，尚未冻结；不在本章节指定 Web 技术栈、API 路径、消息字段或数据库方案。

## 2. 本章术语

| 术语 | 本章含义 |
| --- | --- |
| 训练 | 用户一次开始至结束的训练活动，包含若干动作及组。 |
| 动作 | 用户开组前选定的运动类型。当前不要求系统自行识别动作。 |
| 组 | 对一个已选动作连续完成的一段计次活动，由开始/结束边界限定。 |
| 次 | 完成一个约定的完整动作周期；不完整动作不计为完整次，具体动作口径评审确认。 |
| 估计次数 | 算法对该组给出的计次结果，未经用户修正。 |
| 最终次数 | 用户确认后用于保存、历史和统计的次数，可由人工修正。 |
| 回放 | 对预先录制数据运行算法的验证模式，必须与真实训练区分。 |

与 [#11 术语表](https://github.com/Team-Party-A/repflow/issues/11) 汇总时，以评审后的统一术语为准。单侧交替动作的“一次”不得从腕部观测直接推断双侧总数，需另行确认支持规则。

### 2.1 从开组到保存的最小流程

基于 [Motra 报告 v2（PR #15）](https://github.com/Team-Party-A/repflow/pull/15) 的流程分析，建议原型先走通：选动作 → 手动开组 → 自动计次 → 手动结束组 → 核对/修正 → 确认并本地保存。休息自动识别仍为 Should，不阻塞人工结束与确认。

**组的完成状态与数据传输状态分别表达**：结束计次只冻结本组候选结果，确认保存后才成为完成记录；完成记录可以仍待同步，不能因网络失败倒退成未完成，也不能因已确认就显示“服务器已同步”。以下是用户可观察行为，具体内部状态名及契约另行设计。

| 用户所在步骤 | 可观察结果 | 异常或退出时的规则 |
| --- | --- | --- |
| 已选动作、尚未开组 | 显示动作及是否支持自动计次；次数未开始累计 | 未支持动作明确说明；人工记录入口与自动计次区分，不替代自动计次的 Must 验收。 |
| 计次中 | 显示当前动作、估计次数和结束入口 | 组内短暂停顿不自动新建一组；采样异常提示核对。 |
| 已结束、待核对 | 停止接受该组新增计次，可修改候选次数 | 返回修改不创建第二组；放弃时明确未保存的内容，其他已确认组不受影响。 |
| 已确认并本地保存 | 同一组在历史中出现一次，采用最终次数 | 重复点击确认不新增重复组；网络失败保留本地结果。 |
| 等待同步/同步失败 | 显示待传输或失败，提供明确恢复路径 | 不把失败记录当作服务器已有记录，也不把“清除记录”作为重试。 |
| 已同步 | 可在已同步历史及 Web 中查询 | 重试、刷新不重复增加组；修正后的值须在同步成功后反映到 Web。 |

## 3. 计次算法需求

### REQ-ALG-01：已选动作的组内自动计次

- **用户故事**：作为训练者，我希望先选动作再开组，组内自动记录完成次数，减少逐次手动输入。
- **MoSCoW**：Must。
- **负责模块**：Nessa 负责算法规则与离线验证；Iridescent 负责 watchOS 集成与显示；与 iOS 的记录交接由相应负责人评审。
- **验收标准**：
  1. 给定已选择的受支持动作，开始新组后次数为 0；输入有效传感器样本后只累计该组的完整动作。
  2. 对同一段固定输入与同一参数重复运行，最终总数相同；上一组的缓存和次数不带入新组。
  3. 用户结束组后不再把后续拿放器械动作计入该组；新组开始前不计次。
  4. 首批支持动作名单、动作周期定义及误差门槛在需求评审中确认，以真实留出数据验收；未支持动作明确提示，不伪装为已准确检测。
  5. 对已选的同一受支持动作，分别录制 1 次、2 次短组与 0 次空组，逐项报告估计结果；完整短组允许核对并保存，不因未达到 3 次而静默丢弃。算法误差仍按评审后的门槛验收。
  6. 待机及已开组两种状态分别测试喝水、拿放器械；待机时不累计，已开组内的误触发作为负样本误计单列，不用组后人工修正掩盖算法错误。

### REQ-ALG-02：组后核对与人工修正

- **用户故事**：作为训练者，我希望计次出错时能修改本组次数并保存正确的训练记录。
- **MoSCoW**：Must，作为自动计次与训练记录可用性的补充。
- **负责模块**：Nessa 定义估计值/最终值语义；watchOS、iOS 负责人实现各自已确认的编辑与保存入口。
- **验收标准**：
  1. 给定算法估计 9 次，用户修正为 10 次并确认，重新打开记录时最终次数为 10，相关统计采用 10。
  2. 未经修正直接确认时，最终次数等于当前估计次数；取消编辑不改变原有确认值。
  3. 拒绝负数、非整数等无效次数，并给出可理解的提示；0 次是否保存由全组记录规则统一确定，未确定前不得静默保存为有效训练组。
  4. 人工修正不能用于改写评估数据真值或覆盖算法原始误差；产品是否持久化估计值及修正来源由记录契约评审决定。
  5. 给定第一组已确认 8 次、第二组估计 9 次，将第二组改为 10 次并确认后，两组分别为 8 和 10；修改当前组不得隐式覆盖其他已确认组。
  6. 给定本组已经结束、尚未确认，拿放器械或回到核对页不增加估计次数；重复确认只保留一份本地完成记录。后续传输去重由同步契约共同保证。

### REQ-ALG-03：传感器异常与计次失败可见

- **用户故事**：作为训练者，我希望设备采样或计次异常时收到明确反馈，能够核对已有次数，而不是误以为系统正常工作。
- **MoSCoW**：Must，属于自动计次失败路径。
- **负责模块**：Nessa 提供可判断的异常条件；Iridescent 处理权限、采样状态与提示；保存由 Apple 端负责人衔接。
- **验收标准**：
  1. 传感器不可用或权限不满足时，显示原因及可采取的操作，不显示虚假的“自动计次中”。
  2. 回放包含非法数值、乱序时间戳或持续采样中断的片段时，不把异常样本补成动作事件；具体中断时长阈值评审确认。
  3. 异常后已有确认记录保留，用户可核对、修正或结束本组；恢复采样不重复累计中断前已确认事件。

### REQ-ALG-04：组间休息自动识别

- **用户故事**：作为训练者，我希望组结束后能看到休息状态，减少切换操作。
- **MoSCoW**：Should，Must 稳定后实现。
- **负责模块**：Nessa 与 Iridescent；识别和界面规则共同评审。
- **验收标准**：
  1. 使用独立标注片段验证训练/休息切换；动作过程中短暂停顿不得直接当作新组。
  2. 用户能够人工结束组及确认开始下一组，自动识别不能成为保存训练的唯一通道。
  3. 休息状态不继续累计动作次数；状态切换不丢失上一组已确认记录。
  4. 区分“动作结束时刻”与“用户稍后确认时刻”；修改次数不重置已经开始的休息计时。计时起点和短暂停顿阈值由相关负责人评审，不能把每次静止都直接判定为结束组并保存。

## 4. Web 看板需求

Web 看板在迭代 3 实现，以下均为 Should；Must 未稳定时可按团队范围规则顺延。默认先做只读看板，读到的是已同步至后端的记录；不要求它获得手机尚未上传的本地数据，也不通过 Web 编辑引入双向同步。

### REQ-WEB-01：登录后查看个人训练历史

- **用户故事**：作为用户，我希望在浏览器查看自己已同步的训练记录。
- **MoSCoW**：Should。
- **负责模块**：Nessa（Web）；hulaoya（鉴权与后端数据访问）；接口另行评审。
- **验收标准**：
  1. 以测试账号 A 登录后，列表显示 A 的训练日期、动作、组及最终次数；页面可进入一次训练的明细。
  2. 无登录凭据或凭据过期时，提示登录，不展示缓存中的他人训练信息。
  3. 账号 A 不得通过改变请求参数读取账号 B 的记录；权限校验必须在服务端完成，不能只隐藏网页入口。
  4. 页面标明“已同步记录”；无记录时显示空状态，不与加载失败混淆。
  5. 测试手机有一条已保存但未上传的记录时，Web 不将其显示为“已同步”；上传成功后刷新可见，重复上传后仍只出现一次。此项需与后端同步用例联调。

### REQ-WEB-02：筛选与基础汇总

- **用户故事**：作为用户，我希望按时间和动作筛选，并看到与明细一致的训练汇总。
- **MoSCoW**：Should。
- **负责模块**：Nessa；聚合数据来自后端，计算职责由接口评审确定。
- **验收标准**：
  1. 时间范围与动作筛选可组合，结果只包含满足两项条件的记录；起止边界和时区在测试用例中写明。
  2. 固定测试数据含 2 次训练、3 组，最终次数为 8/10/12；全量结果应为 2 次训练、3 组、30 次动作；“训练次数”和“动作次数”分别命名。
  3. 将其中 10 次修正为 9 次并完成后端同步后，刷新看板的动作总次数为 29；删除一组后按剩余记录重算，删除传播规则须与手机单向上传契约一致。
  4. 空结果显示明确的无数据提示；不展示无依据的准确率、恢复分或预测重量。
  5. 模板计划、待确认候选组、录制回放不得作为已完成训练计入汇总；真实记录中人工修正的次数则按最终值计入。不同动作的总次数只表示记录量，不用作跨动作强度或进步的直接排名。
  6. 修改筛选或刷新失败后，旧汇总若保留展示，应同时标明旧筛选范围与更新时间，不能与新筛选的明细混搭。

### REQ-WEB-03：加载、失败及重试

- **用户故事**：作为用户，我希望知道记录正在加载还是加载失败，并能在网络恢复后重试。
- **MoSCoW**：Should。
- **负责模块**：Nessa；错误语义与 hulaoya 对齐。
- **验收标准**：
  1. 进入页面后区分加载中、成功、空数据、失败四种状态。
  2. 模拟请求超时或服务端错误，页面显示失败及重试入口，不把旧结果显示为“最新”。
  3. 网络恢复后重试成功，列表与汇总使用同一筛选口径，不重复叠加旧结果。

## 5. 非功能需求与可验证门槛

本章只提出算法/Web 相关约束，系统全局的离线保存、同步时延与账号行为由相应负责人补齐。下表除 D-16 最低版本外均为待评审提案，尚无真实设备测量结果。

| 编号 | 用户故事/目标 | 级别 | 负责模块 | 验收方式 |
| --- | --- | --- | --- | --- |
| REQ-NFR-ML-01 | 用户在团队最低版本设备上能运行核心计次 | Must | Apple 端、算法 | 依据 D-16，在实际 iOS 17.2.1/watchOS 9.6.3 测试配置验证启动、开组、计次、修正和保存；其他设备记录实际版本，新设备结果不能替代最低版本验证。 |
| REQ-NFR-ML-02 | 用户断网时仍能完成本地组内计次 | Must | watchOS、算法，iOS 衔接 | 已准备好动作且权限满足时，断开外网执行开组/计次/结束，保留结果；网络恢复后的上传、重试和去重按后续契约另行验收。 |
| REQ-NFR-ML-03 | 用户在一个完整动作后及时看到次数 | Must | 算法、watchOS | 提议确认延迟 P95≤1秒；明确事件真值时刻及设备，测量完整动作结束到显示确认的时间；评审冻结前仅为候选门槛。 |
| REQ-NFR-ML-04 | 计次结果在支持动作上可用且有失败解释 | Must | Nessa、Iridescent | 提议各动作 MAE≤1次、至少90%标准组误差≤1次；负样本平均误计≤1次/分钟。三人按人留一验证，报告每动作、每人样本量与最坏组；这些不等同于“90%准确率”。 |
| REQ-NFR-ML-05 | 用户落腕后不丢失正在采集的组 | Must | watchOS、算法 | 在最低系统真机上完成至少一段包含落腕的连续训练；记录实际时长、采样间隔和丢帧情况，确认无静默停采；更长期及耗电门槛经实测再定。 |
| REQ-NFR-ML-06 | 测试人员能复现相同输入的算法结果 | Must（工程验收） | 算法、watchOS | 固定输入、参数和算法版本，比较 Python 因果评估与 Swift 回放总数及事件；回放模式明确标识，不进入真实历史和统计。 |

原始传感器数据、可识别视频、账号密码、token 不提交仓库；测试使用匿名号和专门测试账号。Web 页面不得展示敏感认证信息。性能报告需要设备与真实测量记录，不能以模拟输入说明已在真机达到性能门槛。

## 6. 竞品结论如何进入本章

来源是 [#6 Motra 竞品调研](https://github.com/Team-Party-A/repflow/issues/6) 对官方资料的核查，不是本组已完成的真机体验测试。

| 竞品观察 | 本章需求 | 范围取舍 |
| --- | --- | --- |
| Motra 自动检测后允许确认和修正 | REQ-ALG-01、02 | 借鉴确认闭环；我方动作仍人工选择，不扩展到自动分类。 |
| Watch 先保存、连接恢复后补发 | REQ-NFR-ML-02；跨模块同步条目由组长汇总 | 本地计次不依赖外网；不引入双向同步或云端在线推理。 |
| 实际训练纪录与预测统计并存 | REQ-WEB-02 | 首版只显示事实汇总，预测重量和恢复计划不进入 Must。 |
| 复杂自动识别及生成训练需额外能力 | 下表 Could 项 | 不能因竞品有此功能而增加本学期承诺。 |

### 6.1 提交原型前的完整走查

| 用例 | 输入与操作 | 应检查的结果 |
| --- | --- | --- |
| AC-01 标准组 | 已选受支持动作，完成8次，结束并确认 | 同一组只保存一次；同步后明细与统计均为8。 |
| AC-02 短组/空组 | 分别完成1次、2次、0次后结束 | 逐项记录原始估计误差；短组可核对保存；空组按评审口径显式处理，不自动混入完成记录。 |
