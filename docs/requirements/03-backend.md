# 需求规格说明书：后端与同步

版本：v0.2 评审稿；日期：2026-10-19；章节负责人：hulaoya（@hulaoyagg）。关联子任务：[#20](https://github.com/Team-Party-A/repflow/issues/20)；父任务：[#7](https://github.com/Team-Party-A/repflow/issues/7)。

本节按[统一需求骨架](需求规格说明书.md)编排，参考已合入的 [iOS 章节](01-ios.md)。本次交付是需求草稿，描述后端应提供的行为与后续验收方式；尚未实现或执行这些用例。

## 1. 范围与当前约定

已有依据是第 1 次例会的 D-02/D-03，以及 iOS 章节的手机侧行为：

- 账号与数据上传属于 Must；账号采用用户名、密码和 token。
- 训练在手机本地保存，再由手机单向上传；不做后端到手机的下拉同步与多设备冲突合并。
- 同一条记录以最后一次写入为准；“最后”的准确含义仍需对齐。
- 手机保存、修改、删除训练后自动同步；断网或失败时保留本地结果，恢复后补传，重试不产生重复记录。
- Web 看板是 Should，只读取已同步数据；本节的查询需求随 Web 推进，不作为 Must 上传链路的前置条件。

下面条目的 MoSCoW 表示建议的功能优先级。除已有决策及 iOS 行为外，后端细化规则均为评审提案，尤其是文末列出的待决项；当前不冻结 API 路径、请求字段、数据库结构、token 类型或新增依赖。后续修改按评审结果更新；编号一经合入 dev，按统一骨架保留，不随内容修改而重编号。

### 1.1 已确认的后端框架

后端采用 **FastAPI**，与 [AGENTS.md](../../AGENTS.md) 中已有技术栈一致；hulaoya 于 2026-10-19 在本次讨论中确认沿用此方案。

选择理由：

- 本项目后端主要向 iOS 和后续 Web 提供账号、训练记录与同步 API，当前范围集中。
- FastAPI 支持基于 Python 类型声明的数据校验、OpenAPI 文档及交互式接口调试，有利于两端联调和后续接口核验。功能依据见 [FastAPI 官方说明](https://fastapi.tiangolo.com/features/)。
- 沿用已有选型，减少项目初期的学习和选型成本，把工作集中在账号、记录与同步行为上。

框架版本、数据库访问与迁移工具、密码校验库和 token 实现留待后续设计。框架自动生成的接口说明仍需与评审后的 `docs/api/openapi.yaml` 契约核对，不能代替契约评审。本次只补充选型依据，不安装依赖或开始业务实现。

## 2. 账号与数据归属

### REQ-BE-001：注册与登录

- **用户故事**：作为用户，我希望通过用户名和密码注册、登录，以便训练记录归属到我的账号。
- **MoSCoW**：Must。属于 D-02「账号」。
- **验收标准**：
  1. 给定用户名符合约定且未被占用，当注册成功，那么创建一个账号并提供登录凭据，使手机能够直接进入已登录状态。
  2. 给定用户名已被占用，当再次注册，那么拒绝创建，不新增同名账号，并提供可供手机显示「用户名已被使用」的结果。
  3. 给定账号存在且密码正确，当登录，那么获得该账号的有效凭据；用户名不存在或密码错误时，均不能获得凭据。
  4. 给定输入不符合评审后的用户名、密码规则，当注册，那么拒绝创建账号并说明输入错误。
- **负责模块**：后端（@hulaoyagg，主要实现方）、iOS（@wenshare71）。
- **来源**：D-02、D-03；REQ-IOS-001。
- **待决问题**：用户名长度、字符及大小写规则，密码长度规则；错误提示与 iOS 对齐，见 Q1。

### REQ-BE-002：登录凭据校验与失效处理

- **用户故事**：作为用户，我希望只有有效登录凭据才能操作记录，登录失效后也能重新登录继续同步。
- **MoSCoW**：Must。属于 D-02「账号」。
- **验收标准**：
  1. 给定未携带凭据、凭据无效或已过期，当上传、修改或删除训练，那么后端拒绝操作，不改变已保存数据，并返回可识别的登录失效结果。
  2. 给定登录失效，手机仍保留该账号的待同步记录，当重新登录同一账号后补传，那么按正常上传规则处理；不能要求用户清空记录才能恢复。
  3. 当返回登录失效结果时，不将其表述为网络断开；iOS 能据此提示重新登录，避免无限重试无效凭据。
- **负责模块**：后端（@hulaoyagg，主要实现方）、iOS（@wenshare71）。
- **来源**：D-03；REQ-IOS-002、REQ-IOS-011。
- **待决问题**：token 有效期、是否自动续期、退出登录是否同时使服务端凭据失效，见 Q2。本节不指定 JWT 或其他凭据实现。

### REQ-BE-003：账号之间的数据隔离

- **用户故事**：作为用户，我希望其他账号不能读取、修改或删除我的训练记录。
- **MoSCoW**：Must。是账号与训练记录归属的基本约束。
- **验收标准**：
  1. 给定账号 A 已上传一条训练，当账号 B 使用自己的凭据尝试修改或删除该训练，那么操作失败，A 的数据不变。
  2. 给定请求中的账号信息被修改，当其与已验证的登录身份不一致，那么不能据此把记录写入其他账号；记录归属由后端验证。
  3. 给定账号 A 的待同步记录，当手机改为登录账号 B，那么不能直接把 A 的记录作为 B 的记录上传；手机在提交前保留并检查原账号归属。
  4. 后续启用查询时，账号 B 不能通过更改查询参数读取 A 的训练，权限校验由后端执行。
- **负责模块**：后端（@hulaoyagg，主要实现方）、iOS（@wenshare71）；查询侧涉及 Web（@shooterli）。
- **来源**：REQ-IOS-001、REQ-IOS-002；REQ-WEB-001.3。
- **待决问题**：退出后本机记录保留还是删除，以及待上传记录在账号切换时如何处理，见 Q3；本条不赋予后端恢复手机已清除数据的能力。

## 3. 手机到后端的同步

### REQ-BE-004：接收并保存训练记录

- **用户故事**：作为训练者，我希望手机上保存的真实训练能够上传，以便后端保留与手机一致的记录。
- **MoSCoW**：Must。属于 D-02「数据同步到后端」。
- **验收标准**：
  1. 给定手机已有一条训练，含 2 个动作、共 3 组，最终次数为 8、10、12，当上传成功，那么后端保存对应的动作、组、最终次数、训练时间、来源，以及重量（如有）；核对结果为 3 组、30 次动作。
  2. 给定一组由算法估计 9 次、用户修正为 10 次，当上传成功，那么记录采用最终次数 10，不被估计值覆盖。
  3. 给定最终次数为负数或非整数，或填写了负数重量，当上传，那么拒绝非法训练，不把它标为保存成功；缺省重量与重量 0 不混为同一输入。0 次组的接收规则见待决问题。
  4. 模板目标、尚未确认的候选组、录制回放不得作为真实完成训练进入同步后的历史与统计；iOS 在上传前区分数据用途，后端按契约可识别的信息检查。
- **负责模块**：后端（@hulaoyagg，主要实现方）、iOS（@wenshare71）。
- **来源**：D-02、D-03；REQ-IOS-003、REQ-IOS-004、REQ-IOS-009；REQ-ALG-002、REQ-WEB-002。
- **待决问题**：一次提交完整训练还是单组变更、合法次数/重量上限与精度、空训练和时间字段的口径，见 Q4、Q6。iOS 当前手动输入拒绝 0 次，算法章节将 0 次组处理留待评审；后端统一规则需与两端确认，不先决定接受或拒绝。

### REQ-BE-005：修改、重复上传与最后写入规则

- **用户故事**：作为训练者，我希望修改后的数据能正确同步，多次重试也只保留一份记录。
- **MoSCoW**：Must。属于 D-03「同一条记录以最后一次写入为准」。
- **验收标准**：
  1. 给定同一条训练、同一次内容修改，当因为重试而提交多次，那么后端仍只有一条训练，组和次数不重复累加。
  2. 给定训练已上传，其中一组最终次数为 9，当手机改为 10 并同步成功，那么该组为 10，其他未修改的组保持原值。
  3. 给定用户再次修改或增删组，当对应变更同步成功，那么后端明细及后续查询使用新结果，不同时保留成多条重复训练。
- **负责模块**：后端（@hulaoyagg，主要实现方）、iOS（@wenshare71）。
- **来源**：D-03；REQ-IOS-006、REQ-IOS-011；REQ-NFR-002。
- **待决问题**：记录身份、变更先后依据、旧请求处理及“同步成功”对应哪次修改，见 Q4；不以设备时间戳作为已确定的冲突规则。
- **待确认的验收场景**：先改为 9、后改为 10，较旧请求延迟到达或被重试。建议最终仍为 10；是否采用此预期及如何判定新旧，按 Q4 讨论，未确定前不作为已冻结验收。

### REQ-BE-006：删除传播

- **用户故事**：作为训练者，我希望手机删除的训练在后端也不再作为有效记录出现。
- **MoSCoW**：Must。配合 iOS 记录删除与单向同步。
- **验收标准**：
  1. 给定后端已有一条训练，当手机的删除操作同步成功，那么正常记录查询不再返回它，相关统计排除它。
  2. 给定手机断网时删除已上传的训练，当恢复连接并完成补传，那么后端同样不再将其视为有效记录。
  3. 给定删除已成功，但手机未收到响应，当重复提交相同删除，那么结果仍表示该训练已不在有效记录中，不因重复操作损坏其他训练。
- **负责模块**：后端（@hulaoyagg，主要实现方）、iOS（@wenshare71）；Web（@shooterli）在看板阶段验证展示结果。
- **来源**：REQ-IOS-007；REQ-WEB-002.3；D-03。
- **待决问题**：物理删除还是标记删除、是否允许恢复、删除与旧上传如何排序，见 Q5。单向上传本身不会把数据拉回手机，但仍需防止后端被旧请求重新写入。
- **待确认的验收场景**：训练删除成功后，删除前的上传再次到达。建议记录仍不出现在有效历史与统计中；与 Q4/Q5 一并确认，不先指定实现机制。

### REQ-BE-007：失败反馈与补传

- **用户故事**：作为训练者，我希望上传失败后能知道是否需要重新登录或修改输入，并能在恢复后继续同步。
- **MoSCoW**：Must。支撑 REQ-IOS-011 的待同步、已同步、同步失败三种状态。
- **验收标准**：
  1. 当后端明确确认保存成功，且确认对应手机当前这次修改时，手机才能将该训练标为已同步；旧修改的成功响应不能把更新的待同步修改一并标成已同步。
  2. 给定凭据失效、输入不合法或服务端处理失败，那么提供可供手机区分的结果；不以空数据或成功结果代替失败。
  3. 给定手机超时，且后端可能已完成保存，当手机重试，那么遵循 REQ-BE-005 去重；单纯未收到响应不能断定服务端未写入。
  4. 给定网络恢复或用户点重试，那么可继续提交原账号的合法待同步数据；失败不会要求用户删除本地记录。凭据失效须先重新登录，非法输入须先纠正。
- **负责模块**：iOS（@wenshare71，自动触发与本地队列）、后端（@hulaoyagg，保存结果与错误反馈）。
- **来源**：REQ-IOS-002、REQ-IOS-011；REQ-NFR-002；#5、#6（保存与同步状态分开）。
- **待决问题**：自动重试间隔、次数及批量部分失败的处理方式待对齐；先明确可恢复行为，不在本稿指定调度实现。同步时延沿用全局 REQ-NFR-003，不另填未经确认的秒数。

## 4. 后续看板查询

### REQ-BE-008：查询已同步记录

- **用户故事**：作为用户，我希望 Web 只展示属于我的已同步训练，且明细与汇总一致。
- **MoSCoW**：Should。服务于 D-02 的 Web 看板，在 Must 上传链路稳定后推进。
- **验收标准**：
  1. 给定账号 A 有已同步训练，当 A 查询，那么返回 A 的有效记录；未上传的手机记录不出现在结果中。
  2. 给定一条训练完成修改或删除同步，当重新查询，那么明细反映最新有效结果，统计不继续采用旧次数或已删除的组。
  3. 数据筛选与汇总遵循 REQ-WEB-002；列表与汇总对同一范围使用一致的数据口径，不因重复上传而重复计数。
  4. 无记录与查询失败是不同结果，Web 能分别显示空状态和失败提示；身份校验沿用 REQ-BE-002/003。
- **负责模块**：后端（@hulaoyagg，主要实现方）、Web（@shooterli）。
- **来源**：REQ-WEB-001–003；D-02。
- **待决问题**：日期边界、时区、分页及汇总由后端还是前端计算，在看板设计时对齐；不因此新增手机下拉同步。

## 5. 非功能需求

### REQ-NFR-301：凭据与日志安全

- **用户故事**：作为用户，我希望服务端不会保存可直接读取的密码，日志也不泄露登录凭据。
- **MoSCoW**：Must。账号功能的基本约束。
- **验收标准**：
  1. 用专门测试账号注册后检查持久化内容，不保存明文或可逆加密的密码，只保留用于验证的密码摘要；算法与参数在后续设计阶段确定。
  2. 检查注册、登录、上传及失败场景的日志，均不包含密码、token 或认证密钥。
  3. 代码仓库不包含真实账号密码、token、密钥或生产配置；测试数据使用专门测试账号，不使用个人训练记录。
- **负责模块**：后端（@hulaoyagg）。
- **来源**：AGENTS.md 第 3.3、6 节；REQ-NFR-102。
- **待决问题**：密码校验与 token 的实现选型留待设计；本条不授权增加依赖。

### REQ-NFR-302：成功保存的数据可持续读取

- **用户故事**：作为训练者，我希望已收到保存成功的训练不因后端进程重启而消失。
- **MoSCoW**：Must。上传成功应表示完成持久化，不能只表示收到请求。
- **验收标准**：
  1. 给定训练上传成功，当正常重启后端服务并通过测试或查询核对存储，那么训练、组与最终次数保持不变。
  2. 给定存储写入失败，那么不向手机返回保存成功，重试按 REQ-BE-005/007 处理。
  3. 给定修改或删除已成功，当正常重启服务，那么对应的新结果或删除结果仍有效。
- **负责模块**：后端（@hulaoyagg）。
- **来源**：REQ-BE-004–007；D-02「数据同步到后端」。
- **待决问题**：异常中断的一致性用例在确定提交单位后补充；备份周期、灾难恢复和性能门槛属于后续设计与部署议题，本条不作相关承诺。

## 6. 与其他章节的对齐

| Q1 | 用户名、密码的输入规则 | 先确定一致的长度、字符、大小写与空白处理。具体值暂不填，避免两端各做一套校验。 | 后端、iOS |
| Q2 | token 有效期与退出语义 | 首版可采用固定有效期，过期重新登录；暂不增加自动续期。退出是仅清除手机凭据，还是服务端同时撤销，需单独确认。 | 后端、iOS |
| Q3 | 退出/换账号后，本地已同步和未同步数据怎么处理 | 建议待同步内容按原账号保留并隔离，退出前提示风险；换账号不能把旧数据带入新账号。iOS 当前暂默认退出后删除本地训练，若采用保留需修改其待决项；这也关系换机或重装后无下拉恢复的产品边界。 | iOS、后端 |
| Q4 | 写入单位、记录身份与“最后”的含义；单账号是否只由一部手机写入 | 本期建议按一部 iPhone 写入、整条训练覆盖上传，重试保持同一记录身份，并按手机修改先后处理旧请求。整条上传便于核对，但记录变大时传输更多；按组上传更细，却要处理更多关联。若严格按服务器到达顺序覆盖，旧请求晚到可能覆盖新编辑，必须明确接受还是防止。具体排序方式与消息字段不在本稿决定。 | 后端、iOS；影响 Web 展示 |
| Q5 | 删除是否保留标记、能否恢复、如何挡住旧请求 | 建议先保留删除标记，不提供用户恢复入口；旧于删除的上传不能让记录重新出现。物理删除更简单，但仅删除正文不足以处理迟到请求，需另有办法。还需决定未上传就删除是否直接取消本地上传。 | 后端、iOS |
| Q6 | 记录内容的边界 | 非 0 组沿用正整数次数、重量可空或非负；0 次组、空训练、上限与精度待统一。时间保留可识别时区的信息；统计周起点与日界线跟 iOS/Web 一起定。不先承诺模板、原始传感器或回放数据上传。 | iOS、watchOS、算法、后端、Web |
| Q7 | 重试与时延目标 | 自动重试节奏、批量部分失败与本地积压上限留待契约/测试计划；时延仍引用 REQ-NFR-003 的 X/Y/Z，不自行补数值。 | iOS、后端；全局指标由汇总评审 |

本期不扩展：找回密码、邮箱验证、第三方登录、手机下拉同步、多设备冲突合并、Web 编辑、云端在线计次。API、数据库结构、部署与备份方案后续单独设计；新增依赖按项目规范讨论。
