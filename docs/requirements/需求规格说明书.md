## 2. 需求编号规则

### 2.1 格式

```text
REQ-<模块码>-<三位序号>
```

例如 `REQ-IOS-001`、`REQ-NFR-401`。

| 模块码 | 范围 | 所在文件 |
| --- | --- | --- |
| `IOS` | iOS App | `01-ios.md` |
| `WATCH` | watchOS App | `02-watch.md` |
| `BE` | 后端与同步 | `03-backend.md` |
| `ALG` | 计次算法 | `04-alg-web.md` |
| `WEB` | Web 看板 | `04-alg-web.md` |
| `NFR` | 非功能需求（全局及各模块） | 本文件第 6 节 |

为什么这样定：

- **模块码对应负责模块**，看编号就知道找谁。`WATCH`、`BE` 用全称或通用缩写，和提交信息的 scope（`watch`、`backend`）对得上；`ALG` 和 `WEB` 分开，是因为两者的级别不同（自动计次是 Must，Web 看板是 Should），实现时间也不同（Web 看板在迭代 3）。
- **序号用三位**，是为了给非功能需求按章节分段（见 2.2），各节作者可以同时写而不会撞号。功能需求一般用不到三位，但统一位数后排序和检索更省事。
- **跨模块的需求**（比如「手机上传后 Web 可见」）只编一个号，挂在主要实现方的模块码下，「负责模块」字段写全参与方。不要在两个章节各写一份。

### 2.2 序号分配

- 功能需求：每个模块码从 `001` 起连续编号。`000` 留给本文件的填写示例，不作为正式需求。
- 非功能需求统一用 `NFR`，按章节分段，各段由该章节作者在自己的文件里编号，汇总时集中列到第 6 节：

| 段 | 归属 | 编写人 |
| --- | --- | --- |
| `NFR-001`–`NFR-099` | 全局（系统版本、离线、同步时延等） | 汇总负责人 |
| `NFR-101`–`NFR-199` | iOS | #18 负责人 |
| `NFR-201`–`NFR-299` | watchOS | #19 负责人 |
| `NFR-301`–`NFR-399` | 后端与同步 | #20 负责人 |
| `NFR-401`–`NFR-499` | 计次算法与 Web 看板 | #21 负责人 |

### 2.3 编号的稳定性

- 编号一经合入 `dev` 就不再改，也不复用。需求删除时保留编号，标题后加「（已废弃）」，并写明原因和废弃日期。
- 需求拆分时，原编号保留为其中一条，新拆出的部分取新编号。
- 草稿阶段使用的临时编号，在合入前按本规则改成正式编号，并在该节文件末尾留一张「临时编号 → 正式编号」对照表，方便追溯评审意见。

## 3. 需求条目的字段

每条需求用一个三级标题，下面是固定的五个字段，另有两个可选字段：

| 字段 | 必填 | 写法 |
| --- | --- | --- |
| 编号 | 是 | 写在标题里：`### REQ-<模块码>-<序号>：<简短标题>` |
| 用户故事 | 是 | 「作为〈角色〉，我希望〈做什么〉，以便〈得到什么〉。」非功能需求可以改写成一句目标 |
| MoSCoW | 是 | Must / Should / Could / Won't 之一，定义见第 4 节；需要说明理由时跟在后面 |
| 验收标准 | 是 | 有序列表，每条可以测试、结果可以观察；尽量写成「给定……当……那么……」。引用其中某一条时写 `REQ-IOS-001.2`（第 2 条） |
| 负责模块 | 是 | 模块名和负责人；跨模块时写全参与方，并标出主要实现方 |
| 来源 | 否 | 来自哪条决策、哪份竞品分析或哪条评审意见，如 `D-02`、`#6` |
| 待决问题 | 否 | 还没定的口径、阈值，或需要其他模块确认的事项 |

量化指标（时延、误差、次数）还没有经过评审时，在数值后面写「（待评审）」，不要写成既定门槛。

目前各章节标「待评审」的事项，按以下方式定稿（第 3 次例会说明）：

- **量化指标**：同步时延 X/Y/Z（REQ-NFR-003）、计次误差（MAE、误差 ≤ 1 次的组占比、负样本误计）、休息计时的起点与停顿阈值、采样中断阈值等，统一在迭代 2 用真机实测数据定稿，检查 3（12-03）前完成。数值由对应模块负责人在算法准确率报告或联调记录里给出，改本文档走 PR。定稿前保留「（待评审）」标记，验收时不作为门槛。
- **非量化事项**：历史列表是否分页、本地未上传记录的数量和保存期限、训练模板是否传到手表，由对应模块负责人在实现该功能的 Issue 里决定，写进验收标准后同步修改本文档。
- **受支持动作**：由双端共享的动作清单确定（`apps/apple/Shared/`），不在本文档列名单。

### 3.1 填写示例

以下仅演示格式，内容不是正式需求，iOS 一节的正式条目由 [#18](https://github.com/Team-Party-A/repflow/issues/18) 填写。

```markdown
### REQ-IOS-000：查看最近的训练（示例）

- **用户故事**：作为训练者，我希望在手机上看到最近的训练列表，以便回顾自己练了什么。
- **MoSCoW**：Must。属于 D-02 的「历史与统计」。
- **验收标准**：
  1. 给定本地已有 3 次训练，当打开历史页，那么按开始时间倒序列出 3 条，每条显示日期、动作数和组数。
  2. 给定本地没有任何训练，当打开历史页，那么显示空状态提示，而不是空白页。
  3. 给定手机处于断网状态，当打开历史页，那么本地已保存的训练照常显示。
- **负责模块**：iOS（@wenshare71）。
- **来源**：D-02。
- **待决问题**：列表是否分页（待评审）。
```

## 4. MoSCoW 定义

级别以 D-02 为基线。章节作者可以把 D-02 中的一项拆成多条不同级别的需求，但不能把 D-02 的 Must 项整体降级；需要调整范围时提到例会。

| 级别 | 含义 | 本项目的判定 |
| --- | --- | --- |
| Must | 没有它，产品不能算完成 | 阶段检查和最终验收必须演示通过；不能顺延 |
| Should | 重要，但 Must 稳定之前不做 | Must 全部通过后再排期；时间不够时可以顺延，需在例会说明 |
| Could | 有余力才做 | 不进入本学期的承诺，不写进阶段计划 |
| Won't | 本学期明确不做 | 写下来是为了防止范围蔓延；不再讨论，除非例会重新表决 |

### 5.1 各节文件的约定

- **文件名**：`<两位章节号>-<英文小写短名>.md`，放在 `docs/requirements/` 下，与上表一致。用英文短名是为了让链接和命令行里的路径不被转义，中文标题写在文件第一行。
- **第一行标题**：`# 需求规格说明书：<章节名>`。
- **开头一段**：章节作者、版本、对应子 Issue。
- **正文**：按第 3 节的格式逐条写需求。可以按功能分组加二级标题。
- **本节的非功能需求**：放在文件末尾的「非功能需求」小节，用第 2.2 节分配的 NFR 段。
- **本节专用术语**：如果术语表（#11）里没有，先写在本节的「术语」小节，汇总时并入术语表。
- **末尾**（如有）：临时编号对照表、待决问题汇总。
- 各节 PR 写 `Closes #<子 Issue>`。

## 6. 非功能需求

本节放全局的非功能需求（`NFR-001`–`NFR-099`）。各模块的非功能需求先写在各节文件里，汇总时按编号段并入本节。

### REQ-NFR-001：最低系统版本

- **用户故事**：作为组员，我希望 App 能装在每个人的真机上，以便全组都能开发、测试和演示。
- **MoSCoW**：Must。
- **验收标准**：
  1. iOS App 的部署目标不高于 iOS 17.2.1，watchOS App 的部署目标不高于 watchOS 10.0。
  2. 在 iOS 17.2.1 的 iPhone 和组内系统版本最低的那台 Apple Watch（watchOS 10.x）真机上，安装、启动并走通一次「选动作 → 开组 → 计次 → 结束组 → 保存」。
  3. 代码中使用高于上述版本的系统 API 时，必须有可用性判断和降级路径；在最低版本真机上不崩溃。
- **负责模块**：iOS（@wenshare71）、watchOS（@whj-thu）。
- **来源**：D-16；第 2 次例会把 watchOS 最低版本由 9.6.3 改为 10。

### REQ-NFR-002：离线可用

- **用户故事**：作为训练者，我希望健身房没有网络时也能照常记录训练，以便不因网络问题丢失数据。
- **MoSCoW**：Must。
- **验收标准**：
  1. 手机和手表都断开外网时，能完成一组训练的计次和保存，训练记录保存在本地。
  2. 断网期间，iOS App 可以查看和修改本地已有的训练记录。
  3. 网络恢复后，断网期间产生的记录能上传到后端，且每条记录在后端只出现一次。
  4. 本地最多可以保存多少条未上传的记录、保存多久（待评审）。
- **负责模块**：iOS（@wenshare71，主要实现方）、watchOS（@whj-thu）、后端（@hulaoyagg）。
- **来源**：D-02、D-03。
- **待决问题**：手表与手机之间断连时，手表侧如何暂存，由 #19 一节补充；上传与去重的具体规则由 #20 一节确定。

### REQ-NFR-003：同步时延

- **用户故事**：作为训练者，我希望训练结束后很快能在后端（以及 Web 看板）看到记录，以便确认数据已经保存好。
- **MoSCoW**：Should。上传本身属于 Must（D-02「数据同步到后端」），这里只约束快慢。
- **验收标准**：
  1. 手表上确认一组后，记录出现在 iPhone 上的时延不超过 X 秒（待评审）。
  2. iPhone 在线时，保存一次训练后，记录出现在后端的时延不超过 Y 秒（待评审）。
  3. 网络从断开恢复后，积压记录全部上传完成的时间不超过 Z 秒（待评审）。
  4. 以上数值在 REQ-NFR-001 的最低版本真机上实测，测试报告写明设备、网络条件和测量方法。
- **负责模块**：iOS（@wenshare71）、watchOS（@whj-thu）、后端（@hulaoyagg）。
- **来源**：D-02、D-03。
- **待决问题**：X、Y、Z 的取值 10-21 例会未定，随手机↔后端（#32）和手表↔手机（#34）两条契约冻结时一并确定。

## 8. 竞品分析结论

来自 [#5](https://github.com/Team-Party-A/repflow/issues/5)（训记）和 [#6](https://github.com/Team-Party-A/repflow/issues/6)（Motra），详见[竞品分析](竞品分析.md)。范围以 D-02 为准，竞品分析不作为新的范围来源。

| 借鉴什么 | 来自 | 落到哪些需求 |
| --- | --- | --- |
| 自动计次后由用户核对、修正再保存；短组不因「至少 3 次」被丢弃 | Motra | REQ-ALG-001、002，REQ-WATCH-003 |
| 修正当前组不改动已记录的组 | Motra | REQ-ALG-002.5，REQ-WATCH-004.2 |
| 「训练 → 动作 → 组」的组织方式，逐组记录，次数可以人工修正 | 训记 | REQ-IOS-004、005、006 |
| 历史回顾与按动作看趋势 | 训记 | REQ-IOS-008、010 |
| 统计只显示实际记录，不显示预测重量、1RM、恢复评分 | Motra、训记 | REQ-IOS-009.4，REQ-WEB-002.4 |
| 本地先保存、恢复后补发；保存状态与同步状态分开显示 | Motra、训记 | REQ-WATCH-004、006，REQ-IOS-011，REQ-BE-007 |
| 休息起点追溯到动作结束，而不是等用户点按；可纠正 | 训记（组员使用反馈）、Motra | REQ-ALG-004，REQ-WATCH-007（Should） |
| 可复用的训练安排 | 训记、Motra | REQ-IOS-012（Should） |

明确不做：未知动作的自动识别、按恢复情况生成训练计划（Could）；社交、Android/Wear OS、App Store 上架（Won't）；饮食、课程、订阅等竞品功能不进入本学期范围。

## 9. 评审结论与跨章节口径

第 2 次例会（2026-10-21）评审通过本需求文档，以下口径已写进各章节：

1. **0 次组**：次数为 0 的组不能保存；核对时显示 0 次，只能修正次数或放弃本组。一组都没确认的训练不生成记录。手动录入、手表核对、后端接收都按这条执行（REQ-IOS-004.2、REQ-WATCH-003.3、REQ-ALG-002.3、REQ-BE-004.3）。
2. **退出登录与换账号**：手机上的训练记录按账号分开保存，退出登录只清除登录凭据，不删除记录；界面只显示当前账号的记录。重新登录同一账号后，记录还在，未上传的继续上传；换成另一个账号，看不到也不会上传前一个账号的记录。手机未登录时不确认手表发来的记录，记录留在手表上。手表消息不带账号信息，手机收到后归到当前登录的账号，训练已经存在的归到原账号（REQ-IOS-002、003，REQ-WATCH-006.6，REQ-BE-003）。不采用「退出即清空」，因为没有从后端拉回数据的功能，清空后重新登录会看到空的历史。
3. **最低系统版本**：iOS 17.2.1、watchOS 10（REQ-NFR-001）。
4. **数据流向**：手表经 WatchConnectivity 把记录交给手机，由手机上传后端，手表不直接连后端（D-03）。
5. **记录身份、接收确认和可识别字段**（REQ-BE-004.4、REQ-BE-005、REQ-WATCH-006.3、006.4）：需求只约定可观察的结果，字段和协议在 [#32](https://github.com/Team-Party-A/repflow/issues/32)（openapi.yaml）和 [#34](https://github.com/Team-Party-A/repflow/issues/34)（手表↔手机消息格式）中定义并冻结。
6. **UI 视觉方案**：[UI 规范](../design/UI规范.md) v0.2（Chalk & Volt）通过，两端原型按它做。
