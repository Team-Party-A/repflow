# 手表 ↔ 手机消息格式 v1（评审提案）

负责人：@whj-thu；接收方审查：@wenshare71；关联 #34。
依据 [watchOS 需求](../requirements/02-watch.md) REQ-WATCH-003–006、REQ-NFR-201，
[iOS 需求](../requirements/01-ios.md) REQ-IOS-002、003、006、007，及 D-03。
本稿经受影响模块负责人批准、合入 dev 后冻结；当前不代表传输代码或真机联调已完成。

## 1. 通道与封装

- 唯一框架为 WatchConnectivity。下述记录、确认及补发通知均用 `WCSession.transferUserInfo`。
- 调用前检查 session 已 activated；未激活先本地排队，激活成功后再投递。无需以 `isReachable` 为前置条件。
- 系统会排队且后台交付，但其回调成功不代表对方业务写库成功；不承诺实时或固定时延。
- 不用 `updateApplicationContext` 覆盖未交接记录，不用 `sendMessage` 兜底可靠交接。
  如以后用 `sendMessage` 做训练中的实时展示，不属于本契约，也不能产生保存确认。
- `userInfo` 为属性列表字典：`type: String`、`version: Int`（固定 `1`，非 Bool）、
  `payload: Data`（UTF-8 JSON 对象）。JSON 可表达 null，**不能直接把 NSNull 放进 userInfo**。
  下文 JSON 示例仅展示解码后的 payload；不是可直接传给 transferUserInfo 的整个字典。
- JSON 禁止重复键、NaN、Infinity，数值字段不能用字符串或布尔值代替。
  未知 type/version 或非法已知字段不写业务库、不回 ack，保留待处理记录并提示升级／处理错误。
  v1 不忽略额外的 payload 字段；变更字段含义、类型或必填性需升 version 并走契约评审。
- 单条 payload 上限建议 64 KiB，结束消息最多 1000 个组 ID；这是本稿应用层提案，不是 Apple 的传输限额。
  超限不截断、不分段冒充完整训练，保留本地记录并显式报错；上限与 #32 一起评审。

[Apple transferUserInfo 文档](https://developer.apple.com/documentation/watchconnectivity/wcsession/transferuserinfo(_:))
规定使用属性列表值及已激活 session。API 在 watchOS 10 基线内；可靠性验收必须用配对真机，不能用浏览器原型或模拟器替代。

| type | 方向 | 含义 | 是否需要业务 ack |
| --- | --- | --- | --- |
| `set_saved` | 手表 → 手机 | 一组经用户确认并已写入手表 | 是 |
| `workout_ended` | 手表 → 手机 | 训练已结束，携带已保存组清单 | 是 |
| `ack` | 手机 → 手表 | 对应记录已持久化处理 | 否，禁止 ack 循环 |
| `retry_pending` | 手机 → 手表 | 登录／接收条件恢复，请检查待传队列 | 否，幂等提示，不含账号 |

## 2. 身份、时间和字段

### 2.1 身份与不可变消息

- 用户开始训练时生成 `workout_id`，开始每组时生成 `set_id`，均用 UUIDv4，序列化为小写标准带连字符字符串。
  没有独立「开始训练」入口时，首个「开始本组」同时开始训练并生成两个 ID。
- 放弃的组不发消息、不复用其 ID；未确认任何组的空训练不发结束消息，也不生成手机训练记录。
- 手机及后端沿用上述 ID，不重新生成。手机手动记录也生成 UUID，不与手表 ID 命名空间另做映射。
- 每个 set_id 只发布一次确认后的不可变快照；保存前核对只改候选，保存后的编辑在手机完成。
  重试保留同一 type/version/ID/内容，不能再次取当前时间或创建新 ID。
- `set_saved` 的业务键为 set_id（全局去重且固定归属一个 workout_id）；
  `workout_ended` 的键为 workout_id。无需额外随机 message_id。
  JSON 键顺序和空白不属于内容；数组顺序有意义。
- `version` 是消息格式版本，**不是** #32 中手机维护的训练 `revision`。
  手机仅在记录内容真正改变时推进 revision；重复消息／ack 不创建修改。

### 2.2 共同格式

时间均为 UTC RFC 3339 字符串，固定毫秒和 `Z`，如 `2026-10-24T10:00:00.000Z`。
`time_zone` 是训练开始时记录的 IANA 标识（如 Asia/Shanghai），补发不改成接收地时区。
业务时间使用事件实际发生时间；与传感器录制契约中的相对单调秒数不是同一字段。
系统时钟跳变造成结束早于开始等非法关系时保留本地并提示处理，不拿手机接收时间伪造。

| payload（set_saved）字段 | 类型与约束 |
| --- | --- |
| workout_id、set_id | UUIDv4 |
| started_at | 训练开始时间；同次训练所有消息一致 |
| time_zone | 非空 IANA 时区；同次训练一致 |
| set_started_at、set_ended_at | 本组开始计次／停止接收计次时刻，不是用户确认保存时刻；started_at ≤ set_started_at ≤ set_ended_at |
| set_index | 本次训练已确认组的顺序，正整数，从 1 连续增加；放弃组不占位；保存时确定后不变 |
| exercise_id | 两端共享代码中稳定的动作键，`^[a-z][a-z0-9_]*$`，1–64 字符；不传显示名称 |
| final_rep_count | 用户确认的整数，建议 1–9999；0、负数、小数不可保存，1／2 次短组合法 |
| estimated_rep_count | 原自动估计的非负整数，建议最大 2147483647；不能用修正后的最终次数回填 |
| record_source | 固定 `automatic`；自动计次后人工修正仍是 automatic |
| weight_grams | v1 手表固定 null，表示未填写；重量录入不是 Watch Must，手机补填后旧补发不得覆盖 |

`set_saved` 只含真实已确认组，不传候选、回放、模板、传感器原始样本或人工标注文件。
无手表手动录组消息；不支持自动计次时引导手机手动记录。

| payload（workout_ended）字段 | 类型与约束 |
| --- | --- |
| workout_id、started_at、time_zone | 与组消息一致 |
| ended_at | 结束训练操作时刻，≥ started_at 且 ≥ 所有已确认组的 set_ended_at |
| saved_set_ids | 非空 UUIDv4 数组，无重复，按 set_index 顺序列出本次**手表曾确认保存**的所有组（含已获 ack 的组） |

结束前必须处理计次中／待核对组：返回核对，或明确确认放弃后结束，不能自动保存候选。
结束快照一经写入即不可变；下一次训练用新 workout_id。
清单是完整性交接依据，不是手机当前记录的覆盖快照；不撤销手机的删组、编辑或额外手动组。

| payload（ack）字段 | 类型与约束 |
| --- | --- |
| ack_type | `set_saved` 或 `workout_ended` |
| workout_id | 被确认消息所属训练 |
| set_id | 仅 ack_type=set_saved 时必填；结束确认必须省略 |

ack 仅表示手机已持久化处理，包括已接收的重复消息或已删除记录的终止处理。
它不代表后端上传，不带用户名、账号 ID、token、归属提示或后端 revision。
手表必须同时匹配 ack_type、workout_id，以及适用的 set_id；未知／不匹配 ack 不删除任何任务。
`retry_pending` 的 payload 固定为 `{}`；丢失时可由后续激活、前台或重试触发补偿。

## 3. 送达、账号与冲突

### 3.1 手表发件箱

1. 「确认并保存」在一次本地事务中保存本组及不可变待传消息。写入失败保留候选、显示保存失败，不发消息。
2. 结束训练时原子保存结束状态与清单消息；失败不报告结束成功，保留可重试入口。
   结束不会清掉已保存组或其待传任务。
3. 系统传输队列不是业务发件箱。进程退出／重启后从持久化发件箱恢复。
   检查 `outstandingUserInfoTransfers`，同一业务键已有在途传输时不重复排队。
4. 只有匹配的业务 ack 才原子标记交接完成；`didFinish userInfoTransfer` 成功不清任务。
   明确传输失败显示「传到手机失败」，无 ack／断连显示「待传到手机」。
5. 已保存未 ack 的记录不得按时间、数量或结束训练自动淘汰；容量不足应提示处理。
   收到 ack 后可释放该消息的重试副本；训练未结束时仍须保留清单 ID 和摘要，以构造结束消息。
   已交接记录的界面保留期是实现参数，不能破坏尚待发出的结束清单。

### 3.2 手机接收事务与归属

- 无当前登录会话时：不创建业务记录、不回 ack；不把消息当作已交接。不能依赖系统重复投递，副本仍由手表保留。
  手机登录成功或 session 重新激活且已登录时，投递合并后的 retry_pending；手表收到后补发未确认消息。
- 已登录时先查本机**跨账号的 workout_id 归属索引／删除标记**：存在则始终归原账号；
  不存在则在首条合法消息被持久化时绑定当前账号。绑定与写入同一事务，避免换账号竞态。
  事务中重验登录会话，退出则回滚，不把处理中的新训练归给下一账号。
- 例如 A 的已知训练在 B 登录时收到后续组：写 A 的隔离本地区域并回 ack；B 的界面不展示 A，
  也不用 B 的 token 上传 A。A 再登录后才上传 A 的待同步记录。
- 结束消息先到也可建立带原账号归属的待完成交接条目，但**没有组不创建可见训练、不计统计、不上传空训练**。
  后续组沿用该归属。手机换机／卸载后本地归属索引消失的恢复不在 v1 保证范围内。
- 首次组消息：在一个事务中写归属、原始接收快照、组、待上传修改；持久化成功后才发送 ack。
  手机本地写入失败不 ack，手机离线不阻碍本地接收，后端失败也不撤回手机 ack。
- 已接收的 set_id：先比所属训练及原始接收快照；相同则不再插入／覆盖，只重发 ack。
  不与手机编辑后的业务值比较，否则会把合法补发误判冲突。跨训练复用 ID、同 ID 不同原始内容、重复 set_index
  或共同训练元信息不一致，均不覆盖、不成功确认；记录不含敏感原文的诊断并保留待处理。
- 手机删除组／训练时，同一事务保留 set_id／workout_id 的归属与删除标记、原始接收依据。
  旧补发命中组删除标记：不恢复该组；命中训练删除标记：不恢复整个训练，也不追加后来才到的组；
  对合法匹配消息持久化终止处理后仍回 ack，避免手表永远补发。删除最后一组按删除整次训练处理。
  v1 删除及接收去重标记不自动过期，不能因退出登录而清理。

### 3.3 结束消息与乱序

Apple 对单个队列按发送顺序交付，但应用重试、跨端回调和持久化恢复仍须幂等，不依赖“结束总是最后处理”。

- 结束先到：保存结束快照与原账号归属，等待清单内各组写入或已删除终止处理；暂不发送结束 ack。
- 组消息各自完成事务就各自 ack；收齐清单且顺序／时间／共同字段一致后，才原子保存结束状态并 ack 结束。
  最后一个缺失组到达也触发完成检查，无须依赖结束消息再发一次。
- 手机保留手表原始交接序列作完整性校验；清单必须覆盖该训练所有已接收手表组且 set_index 对应数组位置。
  有矛盾则保持未完成并提示，不静默删除额外组或伪造结束时间。
- 训练已被手机整体删除时，对合法结束消息持久化终止处理后可直接 ack，不等待被用户删除的内容重新出现。
- 已完成的结束消息重发，确认相同结束快照后仅重发 ack。结束后收到清单外的新手表组视为冲突；
  已存在手机手动新增组不参与手表清单校验。任何旧补发均不能覆盖手机已有编辑或删除。
- 单个组的 ack 只解除该组任务；结束 ack 不能批量清掉尚未取得自身 ack 的组任务。
  全部组及结束消息均取得对应 ack 后，本次交接才全部完成。

### 3.4 补发与用户可见状态

激活成功、App 回前台、收到 retry_pending、手动重试时检查发件箱；可运行期间采用有上限的退避重试，
避免无 ack 时循环入队。具体退避间隔和容量预警在实现／真机联调时确定，不承诺后台定时唤醒。
手机重新登录后的自动补发以系统提供运行机会为前提；没有持续实时连接保证，用户可打开两端并重试。

| 状态 | 条件 |
| --- | --- |
| 已保存到手表 · 待传到手机 | 本地事务成功，尚无匹配 ack |
| 传到手机失败 · 重试 | 系统报告明确失败；数据仍在手表 |
| 已传到手机 | 对应记录收到手机持久化 ack，手机承担后续保留／上传责任 |
| 手机「待同步／同步失败／已同步」 | 由手机与后端协议决定；手表不显示后端已同步，不直连后端 |

Swift 封装示意（错误必须由调用方处理，写库成功后才能调用发送）：

## 5. 与其他契约的对应及待确认项

动作列表在 iOS/watchOS 共享代码维护，不通过本协议同步；`exercise_id` 只查共享字典，
未知键保留待处理并提示更新，不能猜名称。示例 dumbbell_curl 不冻结产品支持名单。
共享实现及动作支持范围由 watchOS、iOS、算法协商，本任务不新增业务动作表。

| #32 / PR #49 对齐项 | 本稿提案与接收方工作 |
| --- | --- |
| W34-ID | UUIDv4 小写、跨端原 ID、冲突不覆盖；手机手动 ID 同规则 |
| W34-EXERCISE | 稳定 exercise_id、共享字典，名单待算法确认；Watch 重量 null，手机可补填 |
| W34-TIME | started_at / ended_at / time_zone 同名同义；组时间仅作交接依据；结束清单保证乱序完整性 |
| W34-COUNT | final_rep_count / estimated_rep_count / record_source 同名；修正不改变 automatic；建议次数范围与 #49 对齐 |
| W34-RETRY | 手机维护 revision；接收快照／去重／删除标记独立于可编辑记录，旧消息不覆盖、不恢复 |

手机映射 #32 时添加 record_kind=actual 与其本地 revision；重量未填映射 null。
未完成结束交接时 ended_at 为 null，不能以最后组接收时间替代。
#49 目前为草案：双方批准各自 PR 后才冻结，不在本 PR 修改后端契约或宣称其待决项已获所有负责人同意。

## 6. 联调验收清单

以下是实现阶段必须执行的用例，本文未声称已在真机完成；原型仅示意状态。

| 用例 | 预期 |
| --- | --- |
| 断连保存 8、10 次两组后恢复 | 同一训练两组各一份，合计 18；ID、估计与最终值不变 |
| 手机写库失败／写成功但 ack 丢失 | 前者不 ack；后者重发只补 ack，不多一组 |
| 收到系统发送成功、尚无业务 ack | 手表仍待传；退出／重启后任务仍在 |
| 未登录收组，之后登录 | 未登录不保存、不 ack；登录提示补发，首次接收绑定当前账号 |
| 已有 A 的训练，在 B 登录时补发 | 归 A，B 不可见且不以 B 上传；A 登录后补传 |
| 手机编辑 10→12、补重量后重发旧组 | 保持 12 与新重量，原接收快照匹配后 ack |
| 手机删组／删除整次训练后补发 | 不恢复；持久化终止处理后 ack；删除标记保留 |
| 先收到结束、后收到全部组 | 无组不出现空训练；收齐后结束 ack；结束先到时的归属不漂移 |
| 结束 ack 先于组 ack 到达手表 | 不清除未确认组任务；重发组仍幂等 |
| 同 ID 异内容／跨训练复用／清单冲突 | 不覆盖，不成功确认，保留待处理并提示 |
| 不匹配 ack、未知版本、非法计次／时区 | 不改已有记录，不清发件箱 |
