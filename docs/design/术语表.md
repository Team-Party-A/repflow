# RepFlow 术语表

版本：v0.1 评审稿；日期：2026-10-19；负责人：whj（@whj-thu）。关联任务：[#11](https://github.com/Team-Party-A/repflow/issues/11)。

本文汇总现有需求中的用语，供需求、原型、代码及测试统一引用。中文定义以已有需求为依据；英文标识符是本次命名提案，待负责人及其他端负责人审阅后采用。本文不定义 API 字段、数据库结构或传输消息枚举。

## 1. 使用与命名约定

- 面向用户统一使用中文；工程讨论可附英文，界面不直接显示枚举名、错误码或 REQ 编号。
- 表中实体／概念用 `UpperCamelCase`，属性／动作／状态值用 `lowerCamelCase`。Python 属性和函数使用对应的 `snake_case`，例如 `estimatedRepCount` → `estimated_rep_count`。
- 保留 [AGENTS.md](../../AGENTS.md) 已有的 `WorkoutSet`、`Exercise`、`repCount`、`WorkoutSession` 用法。不要用裸 `Session`、`Set` 或 `count` 同时指代不同业务概念。
- 表中名称不要求一项对应一个类或存储字段；特别是状态名称仅帮助讨论，不冻结内部状态机。
- 同一用词发生冲突时先核对本表及来源章节；新增定义或变更跨端语义应由受影响模块一起评审。

## 2. 训练与记录

| 中文名 | 英文标识符（建议） | 定义 |
| --- | --- | --- |
| 训练 | `WorkoutSession` | 用户一次开始至结束的训练活动，包含若干动作及组。是产品领域概念，不等同于 HealthKit 的 `HKWorkoutSession` 类型。 |
| 动作 | `Exercise` | 用户开组前选定的运动类型，如哑铃弯举。动作名称不表示系统已自动识别该动作。 |
| 组 | `WorkoutSet` | 对一个已选动作进行的一段计次活动，有明确开始与结束边界。一组内可以短暂停顿，停顿不自动产生新组。 |
| 次 | `Repetition` | 一个完整动作周期。每种动作的起止姿态及单侧／双侧口径待评审，不能把一个信号峰或一只手的运动直接等同于一次完整动作。 |
| 次数 | `repCount` | 一组中动作完成次数的通称。计次中显示估计次数；确认记录、历史及统计使用最终次数。上下文不明确时必须写全限定词。 |
| 估计次数 | `estimatedRepCount` | 算法对本组给出的计次结果，未经用户修正。算法评估使用原始估计结果，不以人工修正掩盖误差。 |
| 最终次数 | `finalRepCount` | 用户确认后用于保存、历史和统计的次数；可等于估计次数，也可经过修正。手动录入并保存的组也有最终次数。 |
| 重量 | `weight` | 用户为一组填写的负荷，可不填；填写时非负。未填写不等于 0。单位、精度及双侧动作按单侧还是合计记录，待评审。 |
| 训练记录 | `WorkoutRecord` | 对训练及其已确认组的持久化记录，可在手机上查看、修改、删除。该术语描述保存结果，不要求新增一个独立模型类。 |
| 已确认组 | `confirmedSet` | 用户确认且已成功本地保存的组。同一组重复确认或重复传输，不能变成多份记录。 |
| 训练模板 | `WorkoutTemplate` | 可复用的动作组合与顺序，属于 Should。模板或计划目标本身不计入已完成训练。 |
| 历史 | `workoutHistory` | 已保存训练的列表及详情。iOS 可显示本地待同步记录；Web 只显示后端已同步记录，展示范围须明确。 |
| 训练次数 | `workoutCount` | 指定范围内的训练数量，与动作次数区分。例如 2 次训练不表示做了 2 次动作。 |
| 总组数 | `setCount` | 指定训练或统计范围内的有效已确认组数量。 |
| 动作总次数 | `totalRepCount` | 指定范围内各有效已确认组最终次数之和。表示记录量，不直接代表跨动作的训练强度。 |

示例：一次训练包含哑铃弯举 2 组（8 次、10 次）和肩推 1 组（12 次），显示「1 次训练 · 3 组 · 动作总次数 30」。将第二组改为 9 次后，总次数为 29；其他组保持不变。

来源：[iOS 需求](../requirements/01-ios.md) REQ-IOS-003–009、012；[算法与 Web 需求](../requirements/04-alg-web.md) 第 2 节、REQ-WEB-002。

## 3. 操作、计次与休息

| 中文名 | 英文标识符（建议） | 定义 |
| --- | --- | --- |
| 选择动作 | `selectExercise` | 在开组前指定本组动作；当前 Must 使用人工选择。 |
| 开始训练 | `startWorkout` | 开始一次训练活动；不表示每个组都已开始采样或计次。是否需要单独按钮由两端原型确认。 |
| 开组 | `startSet` | 开始当前动作的一组，从 0 次起计；界面按钮写「开始本组」。 |
| 自动计次 | `automaticRepCounting` | 对已选的受支持动作，根据传感器输入估计组内次数。它不包含未知动作的自动分类。 |
| 自动识别动作 | `exerciseRecognition` | 系统判断用户在做哪种动作，属于 Could，不作为本期自动计次的前置能力。 |
| 结束组 | `endSet` | 停止为当前组接受新增计次，进入核对阶段；界面写「结束本组」。此时尚不能宣称本组已保存。 |
| 待核对 | `awaitingConfirmation` | 本组已结束，候选结果等待用户核对、修正或放弃；尚不进入历史与统计。 |
| 修正次数 | `adjustRepCount` | 用户修改当前组的候选次数，或修改已保存组的最终次数；不能隐式改动其他组或算法评估真值。 |
| 确认并保存 | `confirmAndSaveSet` | 用户确认候选结果，并将本组保存到本地。仅在本地保存成功后显示「已保存」。 |
| 放弃本组 | `discardSet` | 丢弃尚未保存的本组候选结果；其他已确认组不受影响。与删除已保存记录区分。 |
| 结束训练 | `endWorkout` | 结束整次训练活动，与结束某一组区分。若尚有待核对组，应明确提示如何处理，具体交互由 #19 确认。 |
| 组内停顿 | `intraSetPause` | 同一组中暂时停止目标动作后继续；不因此自动结组、保存或开新组。 |
| 组间休息 | `RestInterval` | 相邻组之间的休息时段。身体停止动作、软件确认结束、用户确认保存是不同事件。 |
| 休息计时 | `restTimer` | 呈现休息时长的计时功能；正计时／倒计时、起点与默认时长待原型评审。 |
| 组间休息自动识别 | `automaticRestDetection` | 算法辅助判断进入休息，属于 Should；误判可纠正，不替代 Must 的人工结束与保存入口。 |
| 来源 | `recordSource` | 一组记录来自「自动计次」还是「手动」。自动计次后人工修正不直接改写为「手动」来源。 |
| 手动记录 | `manualEntry` | 用户直接输入训练与组信息，当前需求由 iOS 提供。与修改自动计次结果区分。 |
| 录制 | `sensorRecording` | 保存带时间戳的传感器样本，供算法开发与验证；不同于保存一条用户训练记录。 |
| 回放 | `sensorReplay` | 对录制输入运行算法的验证模式，应明确标识，不进入真实训练历史和统计。 |
| 采样异常 | `samplingError` | 传感器不可用、样本非法、时间戳异常或持续中断等情况；需提示核对，不能伪装为正常自动计次。 |

来源：[算法与 Web 需求](../requirements/04-alg-web.md) 第 2.1 节、REQ-ALG-001–004、REQ-NFR-406；[iOS 需求](../requirements/01-ios.md) REQ-IOS-003–006；[竞品分析](../requirements/竞品分析.md)。

## 4. 保存、传输与账号

| 中文名 | 英文标识符（建议） | 定义 |
| --- | --- | --- |
| 本地保存 | `localSave` | 将记录持久化到当前设备。手表本地保存、手机本地保存、后端保存是三个不同事实。 |
| 手表到手机传输 | `watchToPhoneTransfer` | 把手表已确认的记录交给 iPhone；不等同于手机已上传到后端。暂存、补发和接收确认由 #19 与 iOS 契约确定。 |
| 上传 | `uploadWorkout` | 手机向后端发送训练的新增、修改或删除结果。当前范围为手机单向上传。 |
| 同步状态 | `SyncStatus` | iOS 某次训练当前修改相对后端的状态，取「待同步／已同步／同步失败」三个用户可见值。 |
| 待同步 | `pendingSync` | 当前修改尚未获得后端成功确认，包括断网等待和发送中的情况。「正在上传」可作临时进度文案，不新增第四个持久状态。 |
| 已同步 | `synced` | 后端成功确认了当前这次修改。旧修改的成功响应不能把更新的修改标成已同步。 |
| 同步失败 | `syncFailed` | 一次同步尝试失败，需要重试、重新登录或修正输入；不表示本地记录已丢失。 |
| 补传 | `retryUpload` | 条件恢复后继续发送未成功确认的变更；仍指向同一条记录，不能每次新建一份。 |
| 去重 | `deduplication` | 同一组或训练重复送达时保持一份有效记录；记录身份及处理机制由后续契约确定。 |
| 删除传播 | `deletePropagation` | 手机删除操作在后端生效，使对应记录不再进入有效历史与统计。 |
| 最后写入 | `lastWrite` | 团队约定的记录覆盖原则；按手机修改顺序还是服务器接收顺序判断，仍待评审。 |
| 离线 | `offline` | 当前所需网络不可用；需要说明是手机无法访问后端，还是手表与手机断连，不能一概显示「未联网」。 |
| 账号 | `UserAccount` | 训练记录的归属主体；不同账号的数据应隔离。 |
| 用户名 | `username` | 注册和登录使用的账号名称；长度、字符与大小写规则待后端和 iOS 确认。 |
| 登录凭据 | `authToken` | 登录成功后用于验证身份的 token；面向用户写「登录状态」，不展示 token 本身。 |
| 登录失效 | `authenticationExpired` | 需要重新登录才能继续操作的认证状态；与网络断开区分。 |

来源：[iOS 需求](../requirements/01-ios.md) REQ-IOS-001–003、007、011；[后端需求](../requirements/03-backend.md) REQ-BE-001–007 及第 7 节；[全局需求](../requirements/需求规格说明书.md) REQ-NFR-002、003。

## 5. 容易混淆的表达

| 场景 | 统一表达 | 避免的表达及原因 |
| --- | --- | --- |
| 停止当前组计次 | 结束本组 | 「结束训练」会让用户误以为整次训练都结束。 |
| 确认后本地写入成功 | 已保存到手表／已保存到手机 | 单独写「同步成功」会混淆目的地。 |
| 手表准备交给手机 | 待传到手机 | 「待同步」未写目的地时，容易误认为正在上传后端。 |
| iOS 上传当前修改成功 | 已同步 | 「已发送」不能证明后端已经保存。 |
| 统计展示 | 训练 2 次 · 3 组 · 动作总次数 30 | 只写「总次数 30」易与训练次数混淆。 |
| 自动计次后修正 | 自动计次（已修正） | 不直接标成手动录入；是否持久化修正标记仍待契约评审。 |
| 重量未填 | 未填写／— | 不显示「0 kg」或推断为自重。 |
| 无数据与请求失败 | 暂无训练记录／加载失败 | 失败不能伪装为空历史。 |
