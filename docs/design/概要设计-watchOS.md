# RepFlow 概要设计：watchOS

版本：v0.1 联合评审稿；日期：2026-11-01；负责人：@whj-thu。关联 [#68](https://github.com/Team-Party-A/repflow/issues/68)。系统架构、部署图及跨端数据流统一见[总览](概要设计.md)，本章只描述手表内部职责与交接安排。

## 1. 范围与依据

依据：[Watch 需求](../requirements/02-watch.md)、[交互原型](../prototype/watch.html)、[UI 规范](UI规范.md)、[共享动作清单](../../apps/apple/Shared/Exercise.swift)、[消息契约](../data/02-watch-phone-messages.md)、[录制格式](../data/01-sensor-recording-format.md)、[算法章节](概要设计-算法.md)。字段、范围和时序以冻结契约为准，本章不扩展消息类型。

| 阶段 | 范围 | 交付状态 / 边界 |
| --- | --- | --- |
| 研究录制 #67 / #78 | Core Motion 采样、HealthKit 运动会话、JSON 文件传到手机并分享给电脑 | 已有实现与人工传输验证；用于采集和离线评估，不是训练业务同步 |
| 训练页面骨架 #70 | 选择全部 7 个共享动作、开始/结束一组、核对时手动加减次数 | 独立分支已有本地实现，待负责人真机验证及 PR 交付；不接自动计次或业务同步，不能把手动输入标成算法输出 |
| 后续自动计次与业务交接 | 逐样本估计、确认保存、可靠发件箱与业务 ack | 本章给出目标设计；算法参数、双端联调和真机验收分别完成后才能宣称可用 |

#70 的阶段范围经负责人确认：全部 7 个共享动作均可手动完成一组，明确提示未接入自动计次、仅保存在手表，不发送训练同步消息。此项是对旧原型仅允许自动动作开组的明确调整；不改变冻结的 Watch v1 业务消息，也不代表扩大自动计次支持范围。

## 2. 模块职责与数据归属

| 手表内部模块 | 输入 / 输出 | 职责限制 |
| --- | --- | --- |
| 训练状态与 SwiftUI 页面 | 用户操作 → 当前动作、组状态、估计/核对值、保存结果 | 只在合法状态接受操作；保存失败保留核对内容；不把界面展示当持久化成功 |
| 采样与计次适配 | Core Motion 样本、明确组边界 → 估计次数、采样异常 | 调用算法逐样本逻辑；原估计与最终次数分开，不负责存储或发送 |
| 研究录制 | 录制元信息、原始样本 → 独立 JSON 文件 | 按录制契约导出，未独立标注时真实次数为 null，不从用户修正生成真值 |
| 本地训练存储 | 确认组、训练结束操作 → 持久化快照 | 与发件箱状态一起提交；仅成功提交后更新“已保存”的界面状态 |
| 发件箱 | 持久化不可变消息、匹配的业务 ack → 待传/已确认状态 | 负责重试与恢复；传输完成回调不等于业务确认 |
| WatchConnectivity 入口 | 文件传输、userInfo 与会话回调 | App 内复用一个会话所有者，按传输类型路由；不另建竞争的 delegate |

手表不持有后端凭据，不管理账号，不直连 HTTP API，不承诺后端“已同步”。组 ID、训练 ID 与消息快照属于业务存储；研究文件及其传输状态独立管理，不能送入训练发件箱。

## 3. 训练状态与页面

| 状态 | 用户操作与转换 | 保留的数据与约束 |
| --- | --- | --- |
| 选动作 | 选择动作、开始一组 → 进行中 | 开组前明确动作；开启训练时生成训练 UUID v4 并记录时区；真实开组事件生成组 UUID v4、记录开始时间 |
| 进行中 | 结束本组 → 核对 | 本组计数从 0 开始；记录实际结束时间并冻结原估计；组内不切动作或并行开组 |
| 核对 | 加减最终次数；确认保存 → 组间；放弃 → 组间/选动作 | 不改变原估计；0 次不能保存，1、2 次有效；上限遵循契约；放弃需明确确认 |
| 组间 | 再做一组、换动作、结束训练 → 总结 | 已保存组保留在同一次训练中；新组独立计数；休息提示不影响持久化 |
| 总结 | 查看已确认结果，开始新训练 | 只汇总已确认组；待传组不能因退出总结或开启新训练而删除 |

在进行中或核对状态请求结束整次训练时，先处理当前未确认组，不静默保存、丢弃或绕过核对。放弃组不复用 ID、不占已确认组的连续序号；保存后编辑交给手机。业务时间按契约编码 UTC RFC 3339 毫秒时间，时钟异常不使用接收时间修补。训练确认结束后固定结束时间和已确认组 ID 清单；结束快照不因重试改变。空训练不生成业务结束消息。

界面遵循 UI 规范：每屏一个主要操作；核对页明确显示动作、最终次数与原估计；加减有可见按钮及辅助功能标签，不能只依赖手势。小屏和大字号允许滚动；破坏性操作使用确认提示。#70 尚未接算法时明确显示手动阶段，尚未接业务同步时明确显示仅在手表保存，不显示“已传到手机”。

## 4. 本地保存与恢复（A2-BE-02）

目标实现采用系统文件 API 与 Codable 保存手表本地快照，不新增存储依赖。快照包含训练元信息、已确认组、不可变待传消息及其业务确认状态；研究录制文件单独保存。具体本地结构不是跨端契约，序列化必须带版本并在不兼容或损坏时保留原文件、给出可操作错误，不静默初始化为空库。

确认保存一组时，串行执行：校验 → 使用开组时生成的 ID → 构造组与消息 → 将新快照原子写入 → 发布界面已保存状态 → 调度发送。组和待传消息不得分别落盘，否则可能产生“有组无任务”或“有任务无组”。写入失败保留原快照和当前核对内容，不发送、不导航离开；重试不重复新增组。

训练结束同样先持久化固定的结束快照，再等待全部组 ack；它不允许新增已确认组。应用重启从快照恢复已保存组、待传任务和已确认集合，检查是否具备发送结束消息的条件。重试保持原 ID、时间、次数字段及结束清单，不重新采样或生成业务内容。

尚未确认的候选与已保存组分开。进程退出后的候选恢复策略需在训练持久化实现时由负责人确认，不能把候选自动变成已保存组。已确认但尚无 ack 的数据不得按超时、数量上限或清理缓存直接淘汰；容量不足时保留已有记录并提示保存失败。已 ack 记录的后续保留策略不在本次设计中擅自规定。

#70 的手动页面记录只用于本地训练骨架，不建立冻结 v1 自动计次消息，也不补造 `estimated_rep_count`。后续接业务同步时，必须明确这些本地记录的处理方式，不能通过改写来源字段直接上传。

## 5. 动作与在线计次（A2-BE-03）

共享动作标识、名称、自动计次标记与负重口径唯一来源为 `Shared/Exercise.swift`，页面和算法适配不各自复制一份清单。首批自动计次为哑铃弯举、哑铃肩推；深蹲在研究阶段先采集。重量口径沿用共享定义，Watch v1 消息的 `weight_grams` 固定为 null，不用 0 代表未知或无负重。

目标计次接口遵循算法章节：已知动作和明确组边界，输入带实际时间戳的样本，以有符号轴向信号、因果平滑和完整周期检测增量更新估计。参数从开发集确定，手表不另设经验阈值；结束时未完成的半周期不额外加次。Swift 实现使用有界状态/缓冲，不为训练计次无限保存全量样本。

采样失败或中断要让训练状态知道并提示用户核对，不能伪装成“真实 0 次”。算法只产生估计与异常，用户修改独立写入最终次数。Python 与 Swift 使用相同固定录制回放比对后再接入页面；误差指标与数据划分引用算法章节，不由页面测试推导准确率。

## 6. 发件箱与手机交接（A2-BE-02）

业务传输采用冻结契约规定的 `transferUserInfo`，信封为版本、类型和 JSON Data 载荷。仅确认保存成功的自动计次组进入 v1 `set_saved`；这不意味着 #70 已实现该链路。

1. 应用启动、会话激活以及契约规定的重试触发时读取持久化任务；对仍在系统传输队列中的同一任务去重，避免每次刷新都追加副本。
2. 系统传输完成仅说明传输层处理结束。未收到匹配的业务 ack，组仍待确认；在 App 可运行的时段有限退避重试，不承诺后台固定周期或立即唤醒。
3. 手机先按账号归属、训练/组 ID、删除标记和重复消息规则执行本地事务；事务成功后发送 ack。未登录不保存、不 ack；已有训练不因当前账号变化而重新归属。实现详见 [iOS 第 5 节](概要设计-iOS.md#5-与手表的边界)。
4. 手表校验 ack 的消息类型、训练 ID、组 ID 等完整身份，匹配后持久化确认状态；无关或重复 ack 不推进其他任务。持久化失败仍按待确认处理，允许重复交接，依赖手机幂等处理避免重复组。
5. 所有已确认组均收到业务 ack 后，才提交该训练固定的 `workout_ended` 消息；结束 ack 也需匹配并落盘。不能仅因所有传输回调成功就发送结束消息。
6. 手机通知重试待传记录时重新调度已有快照。ack 丢失、Watch 重启或手机重放不会改变 ID、覆盖手机编辑或恢复已删除的记录。

界面区分“本地已保存 / 待传到手机 / 传到手机失败·重试 / 已传到手机”，实际状态来自持久化结果与业务 ack。手机向后端上传的成功、冲突与重试归 iOS 管理；手表不根据手机在线、研究文件传输成功或后端请求发起就宣称同步完成。

## 7. 研究录制与运行资源

已有研究录制通过 Core Motion 获取原始数据，借助 HealthKit 运动会话维持落腕采样。开始/停止事件及样本使用一致的单调时间基准换算，样本时间相对首样本；记录实际采样间隔，不用请求的 50 Hz 推导或覆盖真实时间戳。25 Hz 对照与后续参数选择按算法计划执行，不把单次传输成功当成采样质量全面达标。

录制停止后按冻结格式原子落盘，再用 WatchConnectivity 文件传输；手机保存独立文件并通过分享交给电脑。用户导出的原始数据不提交 Git，也不送业务 HTTP API。已完成的落腕与 Watch → iPhone → 电脑人工验证见 #67 / #78；最低系统、长时间运行和训练算法耗电仍需各自验证。

训练采样与研究录制不能同时占用运动会话和采样源。入口在活动会话期间限制切换；停止或错误时释放采样与运动资源，并保留可恢复的数据。接入训练模块时复用现有会话所有者，不让研究文件传输和业务消息处理互相替换 delegate。

## 8. 验证安排与联合确认

| 层次 | 必须覆盖的行为 | 证据来源 |
| --- | --- | --- |
| 页面与状态 | 合法状态转换、重复点击、0 次拒绝、1/2 次保存、加减边界、未确认组的结束/放弃提示 | #70 单元测试、模拟器检查及负责人真机录屏 |
| 存储 | 写失败保留候选、组与任务原子提交、损坏文件保留、重启后恢复待确认状态 | 后续持久化测试；不能用纯内存页面测试替代 |
| 双端交接 | 无 ack、重复/无关 ack、重启、未登录、换账号、删除后重放、全部组 ack 后才结束 | 双端契约测试与配对真机联调 |
| 计次 | 固定回放一致性、采样异常、半周期、负样本与动作覆盖 | 算法评估报告及后续 Swift 对照测试 |
| 可用性与资源 | 小屏/大字号/VoiceOver、落腕、采样与录制互斥、最低系统 | 负责人实际设备验证 |

本章回应 A2-BE-02/03 的设计问题，不宣称相关功能全部完成。待联合确认事项包括：手动本地记录与后续同步的处理方式、未确认候选恢复和已 ack 数据保留策略。公共图及其他模块待确认表述见[总览第 5 节](概要设计.md#5-章节对齐与联合评审)；确认由模块负责人本人完成。
